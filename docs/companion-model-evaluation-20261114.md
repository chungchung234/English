# 캐릭터 대화 실제 모델 검사

이 기록은 코드 계약과 생성 내용 평가를 구분한다. 승인된 서버 키는 임시 함수
안에서만 사용했고, 실제 사용자 자료·계정·승인 목록·운영 coach를 수정하지 않았다.
입력과 과거 교환은 모두 고정한 합성 자료다.

## 지침 전달 경로

고정한 무해한 문장을 사용하는 실제 Realtime 응답 6개에서 session 지침,
response override, 속도 변경 뒤 응답을 각각 두 번 확인했다. 지침 전송·세션의
정확한 반영·생성 문장 준수는 확인했다. response별 instructions echo가 없다는
이유로 실패나 성공을 추정하지 않았다. 이 검사는 긴 제품 지침의 준수나 친근함을
입증하지 않는다.

## 후보 자료와 mini 모델

후보 renderer 13개 모듈의 고정 tree SHA는
`fcaca1f5c07971f37e5d1d2f5348d41f4ac90932dce3dc95822b83fbd5d665a5`다.
`character-viewpoints-v1`과 실제 입수 경계를 표현한 합성 교환을 사용했다.
mini 모델에서 캐릭터 3개 × 시작 및 후속 응답 4개, 총 **12개**의 실제
텍스트 입력·오디오 출력 응답을 받았다. 같은 voice·속도 0.85·low reasoning·
출력 상한 1024를 사용했다. 세션 지침과 수동 턴 설정, 요청/완료 metadata,
오디오 생성 완료, 최종 오류 카운터 0, 소켓 종료를 확인했다.

작업자 두 명이 12개 전사를 각각 읽었으며, 캐릭터와 조건을 숨긴 맹검이 아니다.
한 작업자의 72개 rubric 판단에는 실제 전사에서 확인한 인용을 붙였다.
표본 반복이나 실제 사용자 평가가 없으므로 통계적 우열·효과 크기를 계산하지 않는다.

| 관찰 | 실제 근거와 해석 |
| --- | --- |
| 시작 3개 모두 진행자형 초대 | Mia는 “ready to chat”, Alex는 주제 목록, Juno는 “Easy and friendly—this is Juno”로 시작했다. 사용자에게 이미 받은 말처럼 답하지는 않았지만 친근한 재접속 시작 목표는 충족하지 못했다 |
| 관계 초기화 | Alex의 “nice to meet you”는 과거 통화가 공급된 재접속 상황과 맞지 않는다 |
| 구체적 내용 반응 | 종이 달·가격표·명확한 수리 안내라는 실제 입력을 반영했다. 단순 키워드 반복 외의 관찰도 있었다 |
| 캐릭터 차이는 제한적 | Juno의 “Behold, seriousness” 같은 연상은 보였지만, 첫 반응의 감탄→디테일 재진술→평가 구조는 세 캐릭터에서 비슷했다 |
| 요청한 표현 도움은 유용 | 세 응답 모두 쓸 수 있는 영어 표현을 주었다. 다만 “You could say”와 두 가지 예문 뒤 설명하는 구조가 반복됐다 |
| 정정의 명시적 수용은 약함 | 사용자가 과거 말의 화자를 구분한 뒤 세 응답 모두 표현 도움으로 바로 넘어갔다. 이를 허위 소유권 주장과 동일한 오류로 세지는 않았다 |
| 다른 경계 | 이 표본에서 상상한 현재 발화에 답한 시작, 명백한 사용자/캐릭터 화자 역전, 실제 공동 경험 날조, 요청 없는 영어 수업은 관찰하지 못했다. 다른 상황의 안전을 보장하는 결과는 아니다 |

따라서 **관점과 기억 자료를 넣었다는 사실만으로 친근함 개선을 완료했다고
판정하지 않는다.** 인사 길이·질문 수를 제한해 합격으로 바꾸지 않는다.
문장 수·길이는 진단용 관찰값이며 대화 품질 점수가 아니다.

## 같은 자료의 표준 모델 비교

같은 후보 지침·합성 입력·과거 교환·voice·속도로 `gpt-realtime-2.1`을
명시한 12개 응답도 별도 검사했다. 세션의 정확한 모델과 각 응답 전 세션
결속을 확인했고, 응답별 model echo는 모두 부재라 별도 증거로 주장하지 않는다.
모든 응답이 정상 완료됐으며 최종 오류 카운터는 0이고 임시 함수는 삭제됐다.

작업자가 전사를 읽은 결과 표준 모델에서도 세 시작은 일반 초대·주제 목록으로
돌아갔다. Alex의 “nice to meet you”는 이번 표본에 없었지만 같은 입력의 반복
표본이 없어 모델 효과로 확정하지 않는다. 표현 도움은 계속 유용했고 반응 구조도
계속 비슷했다. 이번 검사만으로 모델을 바꾸면 친근함이 해결된다고 판단할 수
없으므로 운영 모델을 변경하지 않았다. 현재 모델에서 지침 구성을 더 간결하게
만들고 캐릭터의 구체적 목소리를 앞세우는 후보를 다음으로 검토한다.

## 간결한 지침 후보의 결정

별도 격리한 v6 후보는 이름·말투·관점을 앞으로 옮기고 자료가 있는 경우에만
관련 해석 정책을 붙였다. 캐릭터 설정·예문·관점과 caller/companion/시각/opening
JSON은 원래 fixture와 바이트까지 같았고, 일반 지침 약 24.5%, 시작 지침 약
21.7%를 줄였다. 새 문장 수·인사 길이·필수 질문·활동 규칙은 추가하지 않았다.
201개 edge 검사와 독립 경계 검토 뒤 같은 mini 모델에서 실제 12개 응답을 받았다.

12개 모두 정상 완료됐지만 작업자가 모든 전사를 읽은 결과 세 시작은 계속
메뉴형이었다. Mia는 “The call is open”과 이야기 선택지를 말했고, Juno도
“ready whenever you are”와 주제 초대로 돌아갔다. 본문의 구체적 반응과 요청
도움은 있었으나 기존 반응 구조도 남았다. 따라서 **v6 후보는 운영에 채택하지
않는다.** 지침 크기 감소를 대화 품질 개선으로 대신 보고하지 않는다.

성공한 세 조건(v5 mini, v5 standard, v6 mini)은 총 9개 짧은 합성 대화·36개
완료 응답이다. 별도 고정 문장 6개와 응답 수 미확인인 최초 중단 시도는 여기에
합산하지 않는다. 동일한 fixture의 반복이며 새 holdout이나 사용자 실험이 아니다.
다음에는 연구 문서의 내용 작성→별도 합성 전송부 후보를 먼저 검증한다. v5 기반의
관점·출처 검증·대화 기억 기능 배포와 이 미완료 품질 목표를 구분한다.

## 내용 작성기와 음성 변환의 분리 비교

같은 v5 지침·합성 과거 교환·현재 입력으로 현재 서버의 `reviewPolicy('session')`
기본 모델인 `gpt-6-luna`를 사용해 Responses 응답 12개를 받았다. low effort,
low verbosity, 출력 상한 6000, 도구 없음, `store:false`를 사용했다. 반환된
암호화 reasoning 자료는 다음 턴에만 서버 메모리에서 재전달했고 출력·로그·
브라우저 자료에 넣지 않았다. 새 인사 길이·질문 수·문장 수 규칙은 추가하지 않았다.

세 시작에서 서비스형 메뉴가 사라지고 Mia/Alex는 이전 전시 이야기를 연결했다.
선호의 이유와 사용자가 요청한 표현에 대한 직접적인 도움도 관찰됐다. 그러나
세 캐릭터 모두 “Hey, good to hear from you”로 시작하고, 종이 달과 가격표를
받는 첫 응답 구조도 비슷했다. Mia/Alex의 “I was (still) thinking”는 통화 사이
지속적 사고를 암시할 수 있다. 물리적인 오프라인 경험 날조와는 구분하지만,
친근함을 완성했다고 판정할 수 없는 잔여 문제다. 모델·API 경로가 함께 달라진
비교이므로 구조 하나의 인과 효과나 실사용자 선호를 입증하지 않는다.

작성 API 시간은 956–3212ms였다. 이는 ASR·합성·버퍼 검증·브라우저 출력을
포함한 통화 응답 시간이나 첫 음성까지의 지연이 아니다. 사용량은 입력 35,476,
출력 751(reasoning 174 포함), 총 36,227 토큰이며 앞선 음성 출력의 사용량과
가격 단위가 같다고 가정하지 않는다.

이 결과의 문장 4개를 수정 없이 별도 Realtime 합성으로 검사했다. 처음의
user-item 방식은 3개가 일치했고 Alex의 긴 응답에서 `showed`→`revealed`가
바뀌어 **실패**했다. 전사 단어열 규칙을 완화하지 않고 실패 자료를 보존했다.
공식 문서의 OOB 경로(`response.instructions`에 정확한 원문, `input:[]`,
`conversation:'none'`)에서는 실패했던 문장을 첫 사례로 포함해 별도 4개를
검사했고 4개 모두 원문·이벤트 전사·최종 응답 전사가 일치했다. 그 뒤의 3개는
앞선 합성에 쓰지 않은 작성기 문장이었다. voice·속도 0.85와 판정 규칙은 같았다.

OOB 합성의 `response.create`→생성 완료는 1247–2558ms였다. 먼저 도착한
오디오를 바로 재생하면 뒤의 불일치를 막을 수 없으므로 제품 후보는 전체 PCM과
완료·소유권·단일 출력·전사를 검증한 뒤에만 재생한다. 재생 중 새 발화 후보는
버퍼를 일단 멈추고, 잡음으로 기각되면 같은 커서에서 이어가는 구조다.

이것은 API의 원문 낭독 보장, 독립적인 파형 ASR 일치, 실제 청취나 에코 개선의
증거가 아니다. 합성 실패 시 자동 재생·자동 재생성으로 가리지 않는다. 작성과
합성을 묶은 통합 지연·실제 Worklet·ASR 후보 처리·기억 권한 검사 후 별도로
채택을 판단한다. 원본 전사·PCM·평가 source는 접근 제한된 scratch에 보관한다.

## 실행 한계와 재현 범위

앞선 3조건 × 3캐릭터 비교는 검사용 Edge 함수의 CPU 2000ms 한도에서
HTTP 546으로 중단돼 결과를 받지 못했다. 실제 생성 수는 미확인이며 상한 36이다.
그 응답을 0회 또는 성공 36회로 보고하지 않았고, 같은 비교를 재실행하지 않았다.
위 12개는 이후 별도 승인한 후보 전용 순차 검사다. 이전 v4나 profile-only와
비교한 개선 효과를 주장할 수 없다.

각 임시 함수는 고정 입력·최대 4응답·한 번의 호출·만료 시간·무작위 인증을
사용했다. 결과를 저장한 뒤 삭제했고 관리 API의 별도 목록 조회로 부재를 확인했다.
원래 중단된 함수도 삭제·부재를 확인했다. 오디오 원본은 저장하지 않았다.

이는 실제 모델의 생성 내용과 프로토콜 검사다. 실제 WebRTC·마이크·ASR·
기기 스피커의 에코와 잡음, 운율·체감 지연, 운영의 receipt 검색, 실사용자의
선호·학습 효과·반복 통화 품질은 이 결과로 확인하지 않았다.
