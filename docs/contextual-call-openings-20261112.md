# 현재 발화와 과거 맥락을 구분하는 통화 시작

2026년 11월 12일 KST. 기준 소스 `77a8b30`, 직전 앱 배포 `47f15298763890a1690446d97f6899656515bece`. 사용자가 지적한 문제는 말을 하지 않았는데 이미 요청을 들은 듯 답하는 것이었다. 이를 짧은 인사로 제한하고 모든 시작 기억을 없애는 정책과 묶은 것은 과한 제한이었다. 길이가 원인이라는 증거는 없으며, 그 제약은 친구 같은 연속성과 다양한 시작을 줄일 수 있다.

## 변경 원칙

현재 발화를 확인해 응답을 만드는 제어, 시작 응답의 `input:[]`, 사용자 선발화 우선, 같은 통화 재접속에서 중복 시작 방지는 유지한다. 시작 지침은 페르소나·안전·언어·시간 정책을 모두 유지한다. 짧은 인사만 하기·시작 질문 개수·과거 맥락은 나중에만 쓰기라는 시작 전용 강제는 제거한다. 일반 대화의 발언권·목적에 맞는 길이 정책은 계속 적용한다.

시작 지침에는 현재 사용자 발화가 없다는 상태와 선별된 과거 배경을 서로 다른 필드로 준다. 과거 전사 전체, 과거 질문, 교정 예문, 학습 피드백 전체를 다시 넣지 않는다. 문구 금지만으로 해결했다고 평가하지 않고, 서버가 실제로 전달하는 자료와 앱이 응답을 생성하는 조건을 함께 검증한다.

| 상황 | 시작 방향 |
| --- | --- |
| 사용자가 먼저 말함 | 별도 시작을 생략하고 현재 발화에 답함 |
| 현재 통화에 사용자가 직접 준비한 주제가 있음 | 그 주제로 자연스럽게 먼저 말 걸기. 아직 말한 내용으로 인용하지 않음 |
| 최근 적격 대화에 이어갈 구체적 근거가 있음 | 과거의 일임을 구분하며 그 맥락으로 먼저 말 걸 수 있음. 계획 실행·성공은 단정하지 않음 |
| 적격 근거가 없거나 불명확함 | 캐릭터의 말투로 자연스럽게 시작. 기억을 지어내거나 도움 메뉴를 반복하지 않음 |

## 선택과 출처

순수 `buildOpeningContext`는 현재 준비 주제 → 최신 적격 handoff의 사용자 근거 하나 → 일반 시작 순서로 한 방향을 선택한다. `current_utterance:null`은 현재 입력 상태, `continuity`는 과거 배경, `recent_openings`는 표현 반복 회피 참고다. 과거 assistant 문장은 사용자 사실이나 회상 근거로 쓰지 않는다. 선택되지 않은 과거 원문·summary·follow_up 목록은 시작 지침에서 제외한다.

선택 결과에는 실제로 수행할 `action`도 명시한다. 준비 주제 진입, 알려진 결과에 관점 보태기, 미해결 계획 이어가기, 이전 세부와 연결하기, 새로운 구체적 관점 제시를 구분한다. 응답의 목표는 하나의 완결된 대화 기여 후 발언권을 넘기는 것이다. 단어·문장 개수로 인사만 하도록 제한하지 않는다. 최근 시작 자료로 표현뿐 아니라 대화 행동과 각도도 달리하도록 안내한다.

초기 범위는 과거 발화 7일, 시작 표현 14일 내 최대 3개, 표현당 240자다. 이는 검증된 최적값이 아닌 조정 가능한 구현 범위다. 최신 handoff가 비거나 excerpt/analysis fallback이면 오래된 다른 요약을 자동 시작 근거로 승격하지 않는다. 질문·요청·역할극·가정·민감 정보의 보조 검사는 완전한 의미 분류기가 아니다. 불명확한 후보는 일반 시작으로 돌린다. 잊기·수정·제외·보류가 다양성보다 우선한다.

원래 계정·캐릭터의 적격 memory source에서만 시작 표현을 조회한다. 해당 통화의 첫 저장 전사가 assistant인 경우만 사용하고, 사용자 선발화에 대한 첫 답변을 시작 인사로 오분류하지 않는다. 저장된 문장이라는 사실은 실제로 끝까지 재생되었다는 증명이 아니다. 이 자료는 표현 반복 회피에만 쓰며 사실로 재연하지 않는다.

선택한 자료의 eligibility·revision·원문 digest를 기존 service-only RPC로 확인하고, 공급자 교환 후에도 source와 선택 결과를 재검증한다. 제외·부분 기록·보류·원문 변경이 경합하면 오래된 시작 지침을 발행하지 않는다. 현재 계정과 캐릭터 밖의 source와 현재 진행 중 통화는 시작 표현 조회 대상이 아니다. 새 저장 테이블·오프닝 생성 모델·장기 오디오 저장은 추가하지 않는다.

계획의 명확한 ISO 날짜 또는 정확한 오늘/내일/어제 표현은 원래 발화의 시간대에서 달력 날짜로 계산한다. 현재 시각도 같은 시간대의 날짜와 비교해 `upcoming`·`today`·`past`로 전달한다. DST를 24시간 덧셈으로 처리하지 않으며, 시간대가 없거나 표현이 모호하면 `null`이다. 계획 원문은 보존하고, 날짜·검증 절차를 읽어 주는 대신 그 상황에 관한 대화를 시작한다.

## 검증 계획과 한계

선택기와 서버 회귀는 현재/과거 역할 분리, 준비 주제, 질문 전사, 근거 없는 요약, 날짜·출처, suppression·잊기·수정, 동일 계정/캐릭터, provider 전후 source 경합을 확인한다. 브라우저에서는 무발화·잡음·선발화·재접속·취소·긴 통화 요약 제어를 그대로 검증한다. 이번 변경은 마이크 판별기의 소음 정확도를 개선한 것으로 보고하지 않는다.

실제 생성 품질은 production과 동일한 전체 renderer·페르소나와 합성 이력으로 별도 확인한다. ACK·스키마 검사와 실제 문장의 자연스러움·들은 척·과거 요청에 대한 오응답·반복 시작을 구분해 검토한다. 이 소규모 검사는 실제 사용자의 만족도·휴대폰 재생·억양·장기 다양성을 측정한 실험이 아니다.

첫 12개 합성 생성에서 ACK는 모두 통과했지만, 주어진 맥락을 실제로 전개할 긍정 사례 5개 중 4개가 일반 도움 메뉴로 돌아갔다. 따라서 typed 자료의 존재만으로 품질이 해결됐다고 판단하지 않았고, 선택한 action을 실제 대화 기여로 구현하는 지침을 추가했다.

다음 생성에서는 맥락을 사용하기 시작했으나 12개 중 9개가 미완료였다. 이를 잡음 중단과 구분하기 위해 같은 두 prompt를 512/1024 한도에서 각각 한 번씩 비교했다. 한 계획 사례는 512에서 실제 `status_details.reason=max_output_tokens`·출력 512로 끝났고 1024에서는 출력 708로 완료됐다. 다른 사례는 두 한도 모두 완료됐다. 앞선 미완료 9개를 전부 같은 원인이라고 단정하지 않는다.

출력 안전 상한을 1024로 조정하고 요청 한도를 job metadata에 기록한다. 이는 발화 길이 목표가 아니다. 자연스러운 대화 기여를 완결할 여유를 두며, reasoning low·50분 통화 한도·잡음 중단 제어는 유지한다. 이후 실제 `incomplete/max_output_tokens` 수신은 고정 코드의 비내용 진단으로 남겨 소음·사용자 중단과 구분한다. 연결 불안정 경고를 새로 띄우지는 않는다.

1024와 대화 단위·계획 날짜를 반영한 12개 합성 생성은 모두 `completed`로 끝났다. 그 뒤 알려진 결과에 대한 재질문과 neutral 소재 seed를 추가 보완하고, 영향을 받는 세 persona의 일반 시작 3개·요리 맥락 3개를 각각 한 번씩 재검사했다. 이 최종 6개도 모두 완료됐으며, 요리 근거를 사용한 3개는 알려진 결과를 다시 묻지 않았다. 실제로 말하지 않은 현재 요청에 답하거나, 없는 사용자 과거·계획 결과를 단정한 사례는 이 6개에서 관찰하지 못했다. 마지막 6개에 포함되지 않은 준비 주제·계획·억제 검증은 앞 단계 결과와 코드 회귀로 구분한다.

준비 주제·미래 계획 두 사례는 현재 production renderer로 원래 snapshot을 다시 렌더링해 opening/session 지침과 1024 상한이 당시 실제 생성에 쓴 값과 정확히 같음을 별도로 확인했다. [비호출 비교 근거](design/contextual-opening-20261112/unchanged-cases-verification.json)에 기록했으며, 이는 새로운 모델 응답을 생성한 검사가 아니다.

최종 6개의 읽기 검토에서도 서비스형 마무리가 4개에 남았고, 요리 3개는 모두 다음 재료 변형 제안으로 전개됐다. 이 변경은 구조·시작 맥락·미완료 개선 범위이며 친구 같은 자연스러움이 해결됐다는 근거는 아니다. 페르소나 차이와 통화 전체의 서비스형 제안 반복은 실제 새 통화 자료로 후속 평가해야 한다. [생성 및 진단 집계](design/contextual-opening-20261112/generation-evidence.json)는 실패한 단계도 함께 남기고 실제 사용자 품질 점수와 구분한다. 모든 실제 프로브는 고정 합성 자료만 사용했고, 기존 키는 서버 내부에서만 재사용했으며, 임시 함수를 삭제하고 관리 목록에서도 부재를 확인했다.
