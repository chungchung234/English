# 캐릭터가 먼저 통화를 마무리하는 기능 검토

2026-11-11 KST · **검토 문서이며 구현·배포 결정이 아니다.**

## 판단

캐릭터가 먼저 **마무리를 제안하는 방식**은 검토 후보로 남긴다. 사용자의 의사를 확인하지 않고 통화를 끊는 방식은 권장하지 않는다. 기본 흐름은 **마무리 제안 → 사용자 반응 → 짧은 작별 → 실제 음성 재생 완료 → 기존 종료·저장 처리**다.

통화가 끝없이 이어지는 느낌을 줄이고 영어로 작별하는 경험을 제공할 수 있다는 기대가 있다. 반대로 하고 싶은 말이 남은 사용자는 거절당하거나 대화 기회를 빼앗겼다고 느낄 수 있다. 이 기능의 자연스러움·통제감·학습 효과를 확인한 실제 사용자 관찰은 아직 없다. 기대 효과와 권장 흐름은 제품 가설이다.

## 후보 흐름과 사용자 주도권

1. 사용자가 “I have to go”, “오늘은 여기까지”처럼 종료 의사를 명확히 밝히면 캐릭터는 짧게 작별한다. 이미 분명한 의도를 다시 묻는 확인 절차는 넣지 않는다.
2. 캐릭터가 먼저 제안한다면, 작은 대화 주제가 마무리된 경계에서 “Shall we wrap up for today?”처럼 짧게 묻는다. 주제 마무리만으로 종료를 확정하지 않으며, 사용자가 거절한 제안을 반복하지 않는다.
3. 사용자가 동의하거나 실제 작별 의사를 표현하면 종료를 준비한다. 특정 단어가 포함됐다는 이유만으로 판단하지 않는다. 인용·예문·역할극 속 “goodbye”는 실제 종료 의사와 다르다.
4. “조금 더 이야기하자”, 새 질문, 이어 말하기, “아직 말하는 중”, “잠깐 기다려”는 종료 제안을 취소하거나 보류하는 신호다. 침묵·인식 실패·불분명한 반응은 동의가 아니다.
5. 종료가 합의돼도 캐릭터의 짧은 작별이 실제로 재생될 기회를 보장한다. 텍스트 생성 완료만 보고 연결을 끊지 않는다. 그동안 사용자가 다시 말하면, 아직 종료 처리가 시작되지 않은 범위에서 제안을 취소하고 계속 듣는다.

추가 버튼·카운트다운을 기본 화면에 늘리는 방안은 채택하지 않는다. 기존 종료 버튼은 계속 제공한다. ‘생각할 시간’ 버튼을 이번 개선안에서 제외하는 것과 사용자의 말로 표현된 기다림·중단 요청을 존중하는 것은 별개다. 캐릭터의 존재하지 않는 급한 일정이나 외부 의무를 만들어 종료 이유로 제시하지 않는다.

## 종료 근거로 사용하지 않을 신호

- 일정 길이의 침묵, 단어를 찾는 쉼, 늦은 첫 답변
- 짧은 답변, 한국어 사용, 문법 오류, 억양이나 추정 실력
- AI가 추정한 지루함·피로·불만
- 발화량·교정 표현 수·학습 목표를 달성했다는 일방적 판단

특정 초수가 지나면 제안하거나 종료하는 새 기준은 정하지 않는다. 현재 근거로 적절한 고정 시간을 확정할 수 없다.

## 기존 20분 제한과의 구분

현재 클라이언트는 20분에 도달하면 통화를 종료하고 저장한다. 마지막 1분에는 남은 시간을 표시한다. 이는 운영상 통화 제한이며, 캐릭터가 대화 맥락을 판단해 먼저 끝내는 기능과 다르다. [현재 시간 제한 처리](../../web/app.js)

한도에 가까워지면 사실에 근거한 짧은 안내와 작별을 유도하는 방안을 별도로 검토할 수 있다. 한도가 있는 상황에서 계속 대화할 수 있다고 약속하거나, 사용자가 종료에 동의한 것처럼 기록하지 않는다. 연결 장애도 캐릭터가 의도적으로 작별한 사건으로 표현하지 않는다.

## 종료·저장 안전 조건

향후 구현을 결정하더라도 종료 요청은 현재 통화에 묶고, 종료 처리 진입 전까지 취소 가능해야 한다. 사용자 새 발화, 지연된 모델 응답, 재연결, 사용자 종료 버튼이 경합해도 이전 통화의 신호가 다음 통화를 종료하거나 중복 종료를 일으키면 안 된다.

작별 음성 재생 확인과 실제 연결 종료를 분리한다. 종료 처리에 진입한 뒤에는 기존 `endCall()` 경로를 사용해 마이크·상대 음성을 멈추고 마지막 전사, 기기 전송 큐, 같은 통화의 유효한 서버 종료 응답을 확인한다. 전사·저장이 미완료면 완료로 표시하지 않는다. 피드백 준비는 저장 완료와 구분하고, 이미 홈으로 이동한 사용자를 늦은 완료 응답이 다시 끌어오지 않는다. [기존 저장 완료 설계](../save-aware-hangup-20261111.md)

현재 `endCall()`은 진입 즉시 음성을 중단하므로 작별 문장을 생성한 직후 호출하는 것만으로는 이 후보 흐름을 충족하지 못한다. 이것은 향후 설계 시 확인할 경계이며, 이번에 코드를 변경하지 않는다.

## 검증할 질문

- 사용자가 계속 말하려던 순간에 제안하거나 종료했는가?
- 계속하기·기다리기·취소 의사가 반영됐는가?
- 사용자가 종료 이유와 자신의 선택권을 이해했는가?
- 자연스럽게 마쳤다고 느끼는가, 거절당하거나 재촉받았다고 느끼는가?
- 마지막 발화·작별 음성이 잘리거나, 중복 종료·허위 저장 완료가 발생했는가?

먼저 합성 이벤트로 취소·재연결·지연 전사·저장 실패 경합을 검증한다. 그 결과는 기능 안전성의 근거이며 사용자 경험의 증거를 대신하지 않는다. 실제 사용자 관찰에서는 계속 말하려던 의도와 종료 후 설명을 확인한다. 통화 시간이 줄거나 종료 제안 수락률이 높아진 것만으로 학습 효과·만족도 향상을 주장하지 않는다.

## 근거와 적용 한계

- **Schegloff & Sacks (1973), _Opening up Closings_.** [ISCA 저자 아카이브 초록](https://www.conversationanalysis.org/schegloff-media-archive/opening-up-closings-1973/) 확인 범위. 대화 마무리를 턴, 화제, 대화 전체의 순차적 조직과 연결해 논의한다. 종료를 일방적인 정지보다 상호적 과정으로 설계할 근거가 되지만, AI 자동 종료의 효과나 구체적인 대기 시간을 검증한 연구는 아니다. 원문 PDF 전체는 이번 검토에서 읽지 않았다.
- **CEFR Companion Volume과 전화 영어 목적.** [기존 검토](../research/phone-english-purpose.md)는 대화의 시작·유지·종료와 사용자 주도권을 목표로 정리한다. 교육·평가 관점의 근거이며 자동 종료 기능의 효과 실험이 아니다.
- **L2 쉼과 턴테이킹.** [기존 1차 자료 검토](../research/voice-turn-taking.md)는 침묵과 발화 완료를 구분할 필요성을 정리한다. 침묵을 종료 의사로 간주하지 않는 판단을 뒷받침하지만, 이 서비스에 맞는 종료 임계값을 제공하지 않는다.
- **현재 제품 정책.** [공통 대화 지침](../../supabase/functions/coach/core.ts)은 사용자의 주도권, 기다림·복구 신호, 질문 없이 자신의 턴을 마치는 응답을 이미 요구한다. 캐릭터의 한 응답이 끝나는 것과 전체 통화가 끝나는 것은 구분한다.

**현재 상태: 검토 후보. 사용자 요청에 따라 문서만 남기며 구현·배포하지 않는다.**
