# 통화 후 대화 원문과 피드백의 역할 및 준비 상태 검토

> 최신 결정: 비동기 시안의 **2안(읽기는 그대로, 피드백은 따로)**을 선택했다. [구현·검증 기록](implementation/README.md)과 [선택한 시안](async-states/02-separate-feedback.png)을 기준으로 한다.

2026-11-11 KST · 설계 검토용 · 제품 코드와 배포 변경 없음

통화 후 사용자는 먼저 자신의 대화를 확인하고, 준비된 피드백에서 다음 대화에 도움이 될 내용을 찾는다. **원문과 피드백은 모두 중요하지만 준비 시점과 처음 보여줄 비중은 다르다.** 종료 직후에는 이미 받은 대화문을 중심에 두고 피드백 상태를 함께 알린다. 피드백이 완성돼도 읽던 화면을 자동으로 바꾸지 않는다.

앞선 이미지들은 원문과 표현이 모두 완성된 상태만 비교했으므로, 종료 직후의 실제 흐름을 결정할 근거로는 부족하다. 두 탭은 가능한 탐색 수단이며 확정안이 아니다. 피드백을 ‘표현’으로 좁혀 보이게 한 내용 구조도 함께 수정해야 한다.

이 검토를 반영한 [비동기 상태 시안](async-states/README.md)을 추가했다. 준비 중·읽는 중 준비 완료·사용자가 연 피드백을 같은 예시 대화로 비교한다. 기존 아래의 표현 중심 이미지는 이전 초안으로 보관한다.

## 이번 사용자 피드백으로 바뀐 기준

- 통화 화면의 ‘생각할 시간’ 버튼을 개선안에서 제외한다. 음성으로 기다려 달라고 하거나 말을 이어가는 사용자를 존중하는 대화 정책은 유지한다.
- ‘혼자 말해보기’와 수행 자기보고를 통화 후 핵심 흐름에서 제외한다. 해당 기능을 다른 이름으로 다시 끼워 넣지 않는다.
- ‘표현 하나만 챙기기’를 기본 정책으로 삼지 않는다. 실제 대화에서 확인된 교정·다른 표현·잘 쓴 표현을 다루되, 정해진 개수를 채우기 위해 항목을 생성하지 않는다.
- 현재 시각·시간대·기억 전달 건수·정상 저장 문구를 통화 중 상시 노출하지 않는다. 대화 맥락의 시간 정보와 기록 시각 저장은 화면 노출과 분리한다.
- ‘마치기’는 화면 종료만 수행한다. 복습 미루기, 학습 완료, 아는 표현으로 자동 기록하지 않는다.
- 캐릭터가 먼저 끝내는 기능은 [별도 검토 문서](../character-initiated-hangup-review-20261111.md)에만 남긴다.

## 왜 한 표현 제한을 없애는가

한 항목부터 보여주던 선택은 첫 행동의 부담을 줄이기 위한 제품 가설이었다. 논문이 정한 최적 표현 수가 아니다. 기존 [학습 평가 검토](../../research/phone-english-learning-evaluation.md)와 [통화 후 경험 근거](../../research/post-call-experience-20261111.md)도 이 한계를 명시한다. 사용자의 현재 목표는 원문 확인과 여러 유용한 표현의 발견을 함께 지원하는 것이므로, 표현 수를 줄이기보다 설명을 펼치는 깊이를 조절한다.

표현 목록은 피드백의 하위 내용으로 둔다. 필요한 경우 한 줄 제목·짧은 영어 표현·종류로 훑어보고, 항목을 선택해 원문·교정 또는 대안·이유를 확인하게 한다. 뜻이 맞는 표현을 오류로 취급하지 않는다. 같은 오류의 반복은 묶을 수 있지만 출처 발화는 유지한다. 표시 개수는 현재 결과에 따라 달라지며 기존 시안의 4개는 예시다.

## 실제 준비 순서와 종료 화면의 절충

현재 [전사 수신과 종료 처리](../../../web/app.js)에서는 통화 중 받은 대화문을 계속 쌓는다. 종료 순간에 전체 원문을 새로 생성하는 방식이 아니다. 다만 마지막 발화의 전사는 늦게 도착할 수 있으며, 텍스트가 보이는 것과 서버 저장이 확인된 것은 별개다. [피드백 요청](../../../web/post-call.js)은 마지막 전사·전송 큐·서버 종료 확인 후 시작한다. 실제 피드백 평균 생성 시간은 아직 측정하지 않았다.

현재 배포는 저장 확인 후 결과 화면으로 자동 이동하고, 3초 이후 대화문을 먼저 여는 경로를 제공한다. 따라서 ‘데이터가 이미 있음’이 곧 ‘종료 직후 화면에 보임’은 아니다. 저장 완료까지 종료 화면을 유지하는 정책과 원문에 곧바로 접근하는 목표 사이에는 절충이 있다.

이번 검토의 권장은 짧은 종료 연출 뒤 이미 받은 원문을 열고, 저장 상태를 해당 기록에서 안내하는 것이다. 종료 연출은 통화가 끊겼다는 감각을 주고, 저장 여부는 상태 표시가 맡도록 역할을 나눈다. 이는 기존 전환 정책을 바꾸는 설계 후보이며 아직 적용하지 않았다. 마지막 발화나 저장이 미완료인데 완성된 기록이라고 표시하지 않는다.

| 시점·조건 | 원문 영역 | 피드백 영역과 탐색 |
| --- | --- | --- |
| 종료 직후, 마지막 발화·저장 확인 중 | 받은 발화를 읽고, 미확인 상태를 짧게 표시 | 최종 기록 확인 후 준비됨을 알림. 완료된 내용·개수로 선표시하지 않음 |
| 기록 저장됨, 피드백 생성 중 | 저장된 원문 열람 가능 | 준비 중 상태. 사용자가 기다리도록 전체 화면을 막지 않음 |
| 원문을 읽는 동안 피드백 완료 | 읽던 위치 유지 | 진입부의 준비 상태만 갱신. 탭 전환·스크롤 이동·상단 카드 삽입으로 방해하지 않음 |
| 피드백 생성 실패 | 원문과 저장 상태 유지 | 피드백 실패와 해당 재시도만 안내. 기록 손실처럼 표현하지 않음 |
| 결과에 쓸 사용자 발화가 부족함 | 확인된 기록 제공 | 근거 부족과 생성 실패를 구분하고 평가를 채우지 않음 |

## 피드백이 답해야 할 사용자 질문

전화 영어의 목적은 문법 교정만이 아니라 의도 전달, 질문·반응, 이해 실패 복구, 대화의 주도권이다. 다만 이를 매 통화마다 모두 평가해야 한다는 뜻은 아니다. [기존 목적 검토](../../research/phone-english-purpose.md)와 [관찰·성과의 구분](../../research/phone-english-learning-evaluation.md)을 적용해, 확인 가능한 근거와 다음 대화에서의 유용성으로 내용을 고른다.

| 사용자 질문 | 제공할 수 있는 내용 | 제외할 과장 |
| --- | --- | --- |
| 무엇을 계속 써도 될까 | 실제 질문·되묻기·이유 설명 등 근거 발화에 연결한 구체적인 잘된 점 | 채우기용 칭찬, 의도가 전달됐거나 상대 말을 완전히 이해했다는 단정 |
| 다음에는 무엇을 달리 하면 좋을까 | 의미 전달에 영향을 준 교정, 맥락상 도움이 되는 대안과 이유 | 모든 문장을 다시 쓰기, 유효한 표현을 오류로 취급하기 |
| 다시 찾아 쓸 말은 무엇일까 | 교정·대안·잘 쓴 표현의 짧은 목록과 원문 연결 | 한 개 제한 또는 일정 개수를 채우는 규칙 |
| 다음 대화에 참고할 점은 무엇일까 | 이번 관찰과 연결된 작고 선택적인 제안 | 강제 숙제, 이미 목표를 달성했다고 판단하기 |

총평·장점·단점·문법·어휘·발음·목표를 매번 모두 채우는 고정 보고서는 권하지 않는다. 중요한 관찰과 개선점을 짧게 제시하고, 설명·표현·출처는 필요할 때 확장한다. 요약은 과거 기록의 맥락을 찾는 보조 정보로 쓰며 피드백의 핵심 가치를 대신하지 않는다. 교정이 없더라도 근거 있는 잘된 점을 보여줄 수 있고, 근거 자체가 부족하면 짧게 끝낸다.

현재 [서버 분석 스키마](../../../supabase/functions/coach/core.ts)는 요약·잘한 점·교정/대안·다음에 쓸 표현·다음 대화 제안을 이미 포함한다. 반복 패턴은 주간 분석 전용이다. 화면의 표현 중심 구조 때문에 피드백 전체가 교정 목록처럼 보이는 부분이 있으므로, 새 평가 항목 추가에 앞서 기존 결과의 품질과 노출 우선순위를 검토해야 한다.

현재 분석 입력은 전사 텍스트다. 이를 근거로 발음·억양·정확한 말하기 속도·듣기 실력·CEFR 등급·자신감·성격을 점수화하지 않는다. ‘되물었다’는 관찰과 ‘듣기 실력이 좋아졌다’는 능력 판단은 구분한다. 단일 통화에서 장기 습관이나 향상을 확정하지 않는다.

## 기존 시안의 비교 범위

아래 이미지는 두 내용이 준비된 뒤의 공간 배치만 비교한 초안이다. ‘표현’ 라벨, 준비 상태, 피드백의 전체 내용 구조는 현재 검토를 반영하지 않았으므로 최종 구현 대상으로 확정하지 않는다.

| 방향 | 읽기 구조 | 장점 | 확인할 부담 |
| --- | --- | --- | --- |
| 대화와 표현을 나란히 | 고정된 두 탭 사이에서 전환 | 두 종류가 항상 눈에 보이고 공간은 분리됨 | 선택되지 않은 탭의 존재와 개수를 이해하는지 |
| 대화에서 표현으로 | 원문의 관련 발화를 누르면 상세 패널, 표현 모아보기 별도 제공 | 교정이 나온 대화 맥락을 유지함 | 표시된 발화만 눌러야 표현을 찾는다고 오해하지 않는지 |
| 두 화면으로 이어보기 | 원문 전용 화면에서 표현 전용 화면으로 이동 | 각 화면이 하나의 읽기 과제에 집중함 | 표현 확인이 필수 다음 단계나 숙제로 느껴지는지 |

두 탭은 원문과 피드백 진입을 계속 드러내는 유력 후보다. 다만 먼저 `원문 읽기 + 준비 중`, `읽는 중 준비 완료`, `피드백 열람`, `피드백 실패` 상태를 검토해야 한다. 원문과 피드백 근거의 왕복 연결은 어느 구조에도 적용할 수 있다.

## 권장 후보의 동작

1. 두 탭을 채택한다면 같은 통화의 `대화 원문`과 `피드백` 진입이 항상 보인다. 처음에는 대화 원문을 열고, 같은 기록을 다시 방문할 때는 사용자가 마지막으로 선택한 탭을 복원하는 것을 검증한다.
2. 탭마다 읽던 위치와 펼친 항목을 유지한다. 피드백의 근거를 선택하면 해당 발화로 이동하고, 돌아오면 이전 위치를 복원한다.
3. 피드백 생성 중에도 원문을 읽을 수 있다. 준비 완료 시 상태만 갱신하며 현재 읽는 탭이나 스크롤을 자동으로 바꾸지 않는다. 여러 종류의 피드백을 표현 개수 하나로 요약하지 않는다.
4. 교정이 없으면 억지로 생성하지 않는다. 원문은 계속 제공하고 교정 부재·분석 근거 부족·생성 실패를 구분한다.
5. 저장 미확인·일부 전사 누락은 해당 기록 가까이에 표시한다. 저장됨 문구는 서버 확인 후에만 사용하고 피드백 생성과 분리한다. 기존 저장 지연·복구 경로를 유지한다.
6. ‘마치기’는 두 탭과 상세 화면에서 찾을 수 있다. 표현을 모두 열거나 별도 수행 버튼을 눌러야 나갈 수 있는 구조를 만들지 않는다.

## 사용자 검증 과제

- 종료 직후 자신이 한 말을 찾아 달라고 한다.
- 이번 대화에서 쓸 만한 표현을 두 개 골라 보고, 각 표현의 원문으로 돌아가게 한다. 두 개는 과제 예시이지 제품의 고정 개수 기준이 아니다.
- 표현을 읽다가 원문을 확인하고 다시 돌아올 때 위치를 잃는지 관찰한다.
- 피드백이 늦는 상황에서 기록 저장 여부와 표현 준비 상태를 구분하는지 확인한다.
- 완성된 피드백에서 자신에게 도움이 된 구체적인 내용을 설명하게 하고, 실제 의도·원문 근거와 맞는지 검토한다. 서로 다른 피드백 종류가 있다는 사실만으로 유용성을 판정하지 않는다.
- 아무 항목도 연습하거나 선택하지 않고 마칠 수 있는지 확인한다.

성공 기준은 탐색 성공, 잘못 누름, 위치 상실, 저장 상태 오해, 종료·학습 상태 혼동이다. 탭 클릭률이나 표현 열람 개수를 영어 실력 향상으로 해석하지 않는다. 실제 사용자 관찰 결과는 아직 없다.
