# 발화 뒤 응답 지연 개선

이 기록은 2026-11-15(Asia/Seoul) 응답 지연 작업의 측정 범위를 구분한다.
**문장별 재생 실험은 속도 채택 기준을 통과하지 못했으므로 운영에서 활성화하지 않는다.**
이 브랜치는 구현·검증 결과를 보존하는 검토용이며 운영 반영의 증거가 아니다.
실제 승인 계정의 발화 종료부터 물리적 스피커 출력까지 측정한 자료는 아직 없다.
모델 생성, 네이티브 WebAudio, 모의 앱 흐름을 서로 다른 증거로 취급한다.

## 지연을 만드는 구조

기존 작성 대화 경로는 사용자 원문의 저장 ACK → 전체 답변 작성·저장 → 전체 음성
합성·검증 → PCM 전송·검증 → 재생 순서다. 답변의 끝부분까지 합성이 끝나야 첫
소리가 나므로 작성과 전체 음성 준비 시간이 그대로 더해졌다. 전사 완료를 기다리는
시간과 발화 종료 판단 시간도 이 앞에 존재한다.

기존 통합 실험의 5–6초는 helper의 제한된 engineering 확인이었다. 이를 자연스러운
대화의 허용 지연으로 판단하지 않는다. 당시 측정에는 실제 인증·DB·ASR와 사용자
기기의 소리 출력이 포함되지 않았다.

## 첫 단계: 요청 통합과 준비 겹치기

[PR #28](https://github.com/chungchung234/English/pull/28)은 한 요청에서 작성기와
음성 읽기 연결 준비를 겹치고, 현재 통화의 저장 ACK가 이전 통화 업로드를 기다리지
않도록 바꿨다. 현재 원문 ACK·권한·취소·비용·원문과 전사의 일치 검증은 유지했다.
릴리스는 `610e8db97f642253297f45ab723385c93e279c08`이며
[CI 43646545283](https://github.com/chungchung234/English/actions/runs/43646545283)가
성공했다. CI 성공과 별도로 배포 소스·공개 파일 대조를 수행한다.

실제 모델 실험은 독립된 Alex 시작/응답 두 사례의 작성 결과를 각 비교군에서 공유했다.
작성 2회와 읽기 4회를 완료했고, 임시 함수는 삭제 후 별도 조회로 부재를 확인했다.
이 실험은 실제 사용자 대화, 반복 통화 품질, 전체 운영 지연 분포를 평가하지 않았다.

| 네이티브 첫 유효 출력, 요청 시작 기준 | 기존 연결 | 준비 겹치기 |
| --- | ---: | ---: |
| 시작 사례 | 7,706.3ms | 7,675.7ms |
| 응답 사례 | 7,063.7ms | 7,052.5ms |

서버의 검증된 전체 음성 준비는 두 사례에서 약 0.35초 빨랐지만, 브라우저의 첫
유효 샘플은 거의 차이가 없었다. 의미 있는 체감 개선을 입증한 것으로 보고하지 않는다.
두 비교군이 하나의 직렬 HTTP 경로와 동시에 실행된 AudioContext를 공유했고,
PCM 도착 이후 처리 시간도 달랐으므로 이 숫자로 안정적인 속도 차이를 추정하지 않는다.
결과를 지우거나 같은 실험을 다시 실행해 유리한 숫자를 고르지 않았다.

별도의 로컬 초기화 실험은 같은 기존 PCM으로 빈 Worklet 노드를 미리 만드는 방식을
8개 새 Chromium 프로세스에서 비교했다. 첫 유효 출력까지의 중앙값은 48.7ms와
45.3ms였고 방향도 일관되지 않았다. 제품에 이 초기화 변경을 채택하지 않았다.
실제 생성 실험의 긴 admission 시간이 정상 플레이어 비용이라는 주장도 하지 않는다.

## 두 번째 단계: 검증된 문장부터 재생

답변의 내용과 모델·페르소나는 그대로 유지한다. 전체 작성 결과를 먼저 저장한 뒤
자연스러운 문장 경계로 나누고, 각 부분의 합성과 전사·PCM 검증이 끝나면 먼저
재생한다. 다음 부분의 연결 준비와 합성을 재생 시간에 겹친다. 문장 수 제한을
대화 규칙으로 추가하거나 답변을 잘라 짧게 만들지 않는다. 전송 부분이 16개보다
많아지면 나머지 문장을 마지막 부분에 그대로 합친다.

각 부분은 같은 전체 원문의 UTF-8 범위·digest와 원래 통화/턴/권한에 묶인다.
부분을 보내기 직전에도 원문·권한·취소·비용 확인을 다시 수행한다. 합성 예약은
부모 요청 하나이며 전체 출력 한도 4,096 token과 전체 PCM 4.32MB/90초를 공유한다.
앞부분의 실제 사용량을 확인하지 못하면 다음 합성을 진행하지 않는다.

브라우저는 실제 AudioContext 하나를 공유하고 현재 부분과 다음 부분만 네이티브
플레이어에 준비한다. 잡음 후보에는 현재 커서를 보존하고, 기각되면 같은 위치에서
이어 듣는다. 실제 새 발화·중지·통화 종료·계정/권한 변경은 대기 중인 부분도 함께
취소한다. 중간 실패를 전체 재생 완료로 기록하지 않는다.

전체 PCM 합계와 digest, 모든 부분의 강한 출력 완료, 최종 서버 publication,
done과 EOF가 모두 확인돼야 기존 부모 재생 보고를 만든다. 앞부분만 들린 경우를
새로운 공유 기억으로 인정하지 않는 보수적인 정책을 유지한다.

새 capability는 별도 `AUTHORED_DIALOGUE_SEGMENTS_ENABLED` 설정을 요구하고 기본은
꺼짐이다. 기존 전체 음성 경로는 남기되 한 번 부분 재생을 시작한 응답을 자동 재시도하거나
다른 경로에서 다시 읽지 않는다.

## 남은 지연과 검증 경계

문장 재생은 전체 작성기 대기를 없애지 않는다. 발화 종료 판단·전사·현재 원문 저장과
답변 작성 시간은 여전히 첫 음성 앞에 있다. 이번 변경으로 낮은 semantic VAD를
임의로 높이거나 영어를 생각하는 중간 멈춤을 더 빨리 끊지 않는다.
후속 평가에서는 전사 완료 전 구간, 작성, 첫 부분 합성, 네이티브 첫 출력과 문장 사이
대기를 각각 나눠 본다. 실제 PC Chrome·Edge 마이크/스피커 조건의 전체 통화 지연과
자연스러운 억양은 제한된 helper 실험으로 대신 판정하지 않는다.

## 문장별 실제 생성 결과: 비활성 유지

같은 기존 답변 189바이트를 수정하지 않고 기본 3구간으로 나눈 결과와 전체 읽기를
각각 새 브라우저·별도 HTTP 요청·AudioContext에서 순서대로 비교했다. 새 작성기는
호출하지 않았고 실제 읽기 4회를 모두 완료했다. 미확인 생성은 0회이며 임시 함수는
DELETE 후 별도 목록 조회로 부재를 확인했다.

| 고정 원문 준비 이후 구간 | 문장별 3구간 | 전체 읽기 1회 |
| --- | ---: | ---: |
| 브라우저 첫 유효 출력 | 3,230.6ms | 2,714.9ms |
| 서버 첫 검증 PCM 준비 | 2,136.7ms | 1,891.5ms |

문장별 방식이 첫 출력에서 **515.7ms 더 늦었다**. 사전에 정한 최소 500ms 개선
조건을 실패했으므로 기능 플래그를 활성화하지 않았다. 답변의 다음 부분이 오는 동안
첫 부분이 재생됐고 두 후속 부분도 이전 부분의 렌더 종료 전에 준비됐지만, 이 동작
정확성이 속도 개선을 대신 입증하지 않는다. 약 70ms의 native 메시지 간격도 물리적
음향 공백으로 해석하지 않는다. 전사·원문·PCM 일치와 전체 강한 완료는 통과했다.

이 실험은 첫 조건에 차가운 함수·연결 준비를 포함했다. 운영에서는 두 방식 모두
작성 중에 빈 읽기 연결을 준비한다. 이번 실험에 작성기가 없으므로 그 겹치기를
검증하지 못했다. 전체 읽기의 같은 준비 구간을 따로 측정하지 않았으므로 문장별
방식의 준비 시간만 빼서 가상의 개선 수치를 만들지 않는다. 한 고정 답변·한 순서의
결과는 통계적 우열·전체 통화 지연·운율·실기기 청취 검증이 아니다. 같은 실험을
반복해 유리한 결과를 선택하지 않는다.

[실제 원수치와 한계](segmented-component/observed-summary.json),
[정리 확인](segmented-component/cleanup-verification.json),
[첫 단계 실제 결과](prepared-reader-component/README.md)를 보존한다.

로컬 컨트롤러·클라이언트 검사 93개, 통합 네이티브 흐름 12개가 통과했다. 마지막
약한 첫 구간/강한 후속 구간의 native timestamp 검증을 보강한 뒤 해당 구간만 별도로
재검사해 통과했다. 전체 검사 739개 중 새 capability의 기대 모양 한 건이 실패했고,
정확한 새 false 항목을 반영한 관련 서버 검사 130개가 모두 통과했다. 이후 추가한
구두점·이모지 전송 경계 검사도 이 130개에 포함된다. 최종 Deno·문법 검사와
17개 모듈 배포 검증기의 로컬 120개 소스 검사는 통과했다. 이 결과를 CI·운영 배포
검사나 사용자 마이크 통화로 표현하지 않는다.
