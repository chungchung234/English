# 운영 준비 점검 — 2026-11-10

운영 설정 조회, 격리된 OTP 발송 검사와 배포 전 논리 백업·격리 복원 결과다. 이 문서는 배포 완료나 공개 출시 승인을 뜻하지 않는다. 실제 배포 결과는 해당 커밋의 [GitHub Actions](https://github.com/chungchung234/English/actions)에서 DB·함수·웹 작업별로 확인한다.

## 확인한 상태

| 항목 | 실제 확인 결과 | 해석 범위 |
| --- | --- | --- |
| 이메일 로그인 | 이번 점검의 OTP 발송 요청이 HTTP 500으로 실패 | 실제 메일 수신·코드 검증·승인 계정 진입은 통과하지 못함 |
| 관리형 DB 백업 | 보관된 백업 0개, PITR 비활성 | 관리형 복구 수단 확보 완료로 볼 수 없음 |
| 배포 전 논리 백업 | 당시 공개 스키마의 앱 테이블 12개 전체, 합계 0행. 접근 승인 목록과 필요한 최소 인증 소유권 메타데이터 포함 | 고객 이력이 있는 데이터의 복원 성공을 입증하지 않음 |
| 적용 스키마 확인 | 운영 적용 마커 9개와 저장소 마이그레이션 SHA-256 일치 | 당시 미적용인 `202611100012`는 이 백업·복원에서 제외 |
| 격리 복원 | 로컬 PGlite에서 37개 검사 통과 | 운영 DB로 복원하거나 운영 데이터를 변경하지 않음 |

이메일 오류의 과거 진단과 이번 관찰은 구분한다. [이메일 복구 기록](email-login-recovery.md)에서는 SMTP 서버 주소를 수정한 뒤에도 발송이 실패했고, 당시 제공자 로그에서 Gmail `535: Username and Password not accepted`를 확인했다. 이번의 새 HTTP 500 관찰만으로 동일한 SMTP 거부 코드가 다시 확인됐다고 단정하지 않는다. SMTP 설정의 존재도 실제 전달 성공을 뜻하지 않는다.

## 논리 백업·복원에서 검증한 것

- AES-256-GCM으로 암호화했으며 변조된 암호문의 인증 실패를 확인했다. 암호화 파일과 키는 저장소 밖의 별도 파일로 분리하고 디렉터리 0700·파일 0600 권한을 확인했다. 평문 데이터 파일은 만들지 않았다.
- 적용된 마이그레이션만 재생하고, 열·NULL 허용 여부·제약·인덱스·RLS 정책·함수·테이블 트리거를 비교했다. PostgreSQL 18이 별도 기록하는 NOT NULL 제약은 열의 NULL 허용 여부와 함께 비교했다. 제공자의 추가 RLS 보조 함수 정의도 로컬에서 복원했다.
- 복원된 전체 행의 일치, 기본키·외래키, 분석 인용의 소유자·회차 관계, 알 수 없는 인증 계정의 접근 거부를 검사했다. 공개 테이블이 비어 있었으므로 행 일치와 참조 검사는 빈 운영 데이터에 대한 결과다. 최소 인증 범위에 해당하는 계정도 없어 실제 승인 계정의 성공 경로는 검증하지 못했다.

이 사본은 작업 공간에 둔 수동 복구 참고자료이며 영속적인 자동 재해 복구 체계가 아니다. 인증 비밀번호·외부 로그인 제공자·토큰·세션 자격 증명은 복사하지 않았다. 관리형 인증 서비스, 제공자 이벤트 트리거·역할, WAL·물리 복구, 저장소, 함수 비밀값, 호스팅까지 포함한 전체 시스템 복구를 검증한 것이 아니다. 백업·복원 검사 중 운영 데이터·설정을 변경하거나 유료 백업을 활성화하지 않았다. 별도 OTP 발송 검사에 사용한 임시 Supabase 인증 계정은 삭제했다.

## 운영자가 완료할 작업

1. 발송 Google 계정의 2단계 인증과 [앱 비밀번호](https://support.google.com/accounts/answer/185833?hl=ko) 사용 가능 여부를 확인한다. [Supabase SMTP 콘솔](https://supabase.com/dashboard/project/domkmxmwmihcfadophfg/auth/smtp)에서 Gmail 계정에 맞는 앱 비밀번호를 설정한다. 조직 정책상 사용할 수 없다면 허용된 발송 서비스를 선택한다. 비밀번호·인증 코드는 채팅이나 저장소에 남기지 않는다.
2. 발송 제한이 해제된 뒤 인증메일을 한 번 요청해 API 성공, 수신함 도착, 최신 코드 검증, 승인 계정의 앱 진입을 각각 확인한다. 계속 실패하면 반복 발송하지 않고 새 제공자 로그로 원인을 확인한다.
3. 필요한 복구 시점·복구 시간·보관 기간·예산을 정해 관리형 유료 백업/PITR 또는 별도 암호화 외부 보관 정책을 선택한다. 자동 구매·요금제 변경은 하지 않았다. 선택한 방식으로 데이터가 있는 복원 훈련과 보관·키 복구 절차를 확인해야 한다.
4. 실제 승인 계정으로 로그인한 뒤 마이크 권한, 실제 음성 연결·발화·응답, 종료 후 전사 저장·피드백·재접속을 확인한다. 로컬 합성 응답 검사는 이 확인을 대체하지 않는다.
5. 실제 참여자의 통화 종료→표현 선택→연습 또는 건너뛰기→저장 확인→다음 접속 과제 관찰을 진행한다. 사용성·접근성·학습 부담·재방문 효과는 아직 실제 사용자 연구로 검증하지 않았다. 상세 범위는 [기획](post-call-plan.md)과 [로컬 검증 보고서](post-call-validation.md)를 따른다.
