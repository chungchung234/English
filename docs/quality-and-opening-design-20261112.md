# 통화 품질과 반복 시작 및 소음 중단 개선 설계

2026년 11월 12일 KST. 기준 소스는 `b425645`이며, 앱 동작은 공개 빌드 `git:ea6024ae7bf8dedd1bd93014c91e96ded49b85e8`와 같다. 운영 자료는 2026년 11월 12일 00:15 UTC에 확보한 2개 계정의 19개 통화, 전사 345개, 세션 분석 14개와 주간 분석 1개다. 최신 빌드 통화는 짧은 2개뿐이다. 아래는 구현 전 설계이며, 기존 배포의 품질 개선 효과를 측정한 결과가 아니다.

우선순위는 스피커폰의 작은 소음에 발화가 끊기는 문제를 줄이고, 통화 전체의 대화를 함께 만들어 가며, 의도와 불확실성을 올바르게 처리하는 것이다. 시작 문구 교체만으로는 반복적인 대화 경험을 해결하지 못한다. [집계 근거](research/quality-opening-baseline-20261112.json)에는 원문과 실제 계정·통화 식별자를 넣지 않는다.

전사 수신 순서는 실제 소리의 순서와 다를 수 있다. 사용자의 인사에 짧게 인사로 답하는 것은 정상이다. 따라서 첫 세 응답의 인사 개수를 곧바로 중복 인사 오류로 세지 않는다. 문제로 평가할 행동은 이미 대화가 시작됐는데 자기소개·도움 메뉴·일반 질문으로 다시 출발하는 것이다. 명확한 현재 시간대 인사 오류는 이번 검토에서 발견되지 않았다. 밤에 과거의 아침 습관을 언급한 사례는 회상 소재의 관련성 문제와 구분한다.

현재 `web/app.js`의 `activateCall()`은 새 통화의 `greeted=false`를 보고 최초 `response.create`를 보낸다. 같은 통화의 재연결은 막지만 이전 통화의 시작 방식은 보지 않는다. `coach/index.ts`의 `voiceConfiguration()`도 모든 새 통화에 짧은 따뜻한 인사와 선택적 회상을 지시한다. 캐릭터별 말투는 있지만 최근 사용한 시작 전략·질문·주제를 관리하는 상태는 없다. 이는 확인된 구조적 원인이며, 프롬프트와 모델의 상투 표현 성향이 각각 얼마나 기여했는지는 비교 실험이 필요하다.

또한 `memory_context.ready`는 회상할 적절한 소재가 있다는 뜻이 아니다. 최신 통화의 handoff가 빈 `threads`를 가지면 `recentConversation()`에서 빠지고 이전 handoff가 continuity 후보가 될 수 있다. 빈 기억은 정상적인 결과일 수 있다. 이를 오래된 이야기를 자동으로 다시 꺼낼 근거로 사용하지 않는다.

## 통화 전체의 자연스러움

추가 VOC는 같은 인사뿐 아니라 대화가 계속 비슷하고 친구와 이야기하는 느낌이 약하다는 것이다. 기존 기록에서는 내용에 답하기보다 조건부 도움을 제안하며 끝내기, 주제 선택을 다시 사용자에게 넘기기, 사용자의 운영 요청을 교정 예문으로 바꾸기, 오해 뒤 같은 설명을 반복하는 사례가 보인다. 최신의 짧은 두 통화에도 서비스형 제안·긴 AI 활동 설명·과한 감정 해석 후보가 있으나 장시간 대화의 개선 여부를 판단할 표본은 아니다.

전체 assistant 전사 172개 중 `if you want`가 들어간 메시지는 21개다. 선택권을 주거나 실제 도움 요청에 답하는 적절한 쓰임도 포함하므로 오류율로 해석하지 않는다. 평가할 것은 특정 어구의 금지 여부보다 대화 내용 대신 서비스 제안으로 반복 회귀하는 구간이다. 반대로 짧고 뜻을 보존한 표현 도움·직접적인 뜻 설명 뒤 사용자가 감사하거나 이해를 표시한 사례도 있다. 교정과 질문을 전부 없애는 설계로 바꾸지 않는다.

현재 정책은 사용자 주도권·짧은 반응·발언권 반환을 강조하지만, 상대가 이야기에 무엇을 보태야 하는지는 상대적으로 약하다. 또한 `voiceConfiguration()`은 준비한 목표가 없어도 `memory.focus` 표현을 한 번 연습하도록 자연스럽게 초대하라는 지시를 둔다. 일반 대화 정책과 이 학습 지시가 함께 작용해 교사·안내원 같은 흐름을 만들 수 있다. 이는 구조적 원인 후보이며 지침만으로 인과 효과를 확정하지 않는다.

| 바꿀 행동 | 구체적인 응답 정책 |
| --- | --- |
| 공감하고 질문하기를 반복 | 사용자가 말한 구체적 내용에 자기 관점·관찰·관련 정보 중 필요한 것을 보탠다. 다음 질문 없이 한 반응으로 끝날 수도 있다 |
| 매번 사용자가 주제를 골라야 함 | 현재 이야기의 사건·선택·미해결 부분을 이어 간다. 바꾸고 싶다는 신호가 있을 때 자연스럽게 전환한다 |
| 동의·칭찬·도움 제안만 함 | 맥락에 맞는 취향·가벼운 이견·유머도 허용한다. 캐릭터 차이는 반응 관점에서 드러내며 가상의 실제 하루나 함께 겪은 일을 만들지 않는다 |
| 말투만 다른 세 캐릭터 | Mia는 구체적 세부를 받아주고, Alex는 관점·비교를 보태고, Juno는 관련 있는 가벼운 연상을 보탠다. 매 턴 이 특성을 과시하지 않는다 |
| 일반 대화를 학습 과제로 전환 | 준비한 목표나 현재 요청이 있을 때만 표현 도움을 연결한다. `memory.focus`가 있다는 이유만으로 통화 중 연습 초대를 의무화하지 않는다 |
| 같은 오해·설명 반복 | 사용자의 정정이 오면 기존 해석을 버리고 문제 부분 하나를 확인한다. 제품 작동 원리를 길게 설명하며 대화를 덮지 않는다 |

합성 예로 사용자가 “The coffee was good, but it was too noisy.”라고 말하면, 곧바로 카페를 영어로 묘사하는 연습을 제안하기보다 “Good coffee can only make up for so much noise. I’d choose somewhere quieter.”처럼 관점을 보탤 수 있다. 이는 작성한 행동 예시이며 실제 모델의 개선 출력이 아니다. 모든 턴에 의견이나 농담을 하나씩 넣는 할당량도 만들지 않는다.

일반 대화에서는 구체적 내용에 기여하고, 사용자가 표현을 물으면 바로 돕고, 교정·복습은 기본적으로 사후 흐름에서 제공한다. 응답을 전부 짧게 만드는 것으로 자연스러움을 평가하지 않는다. 필요한 설명은 충분히 하고, 상투적인 전제·중복 공감·조건부 도움 메뉴를 줄인다. 대화 중 상태는 현재 주제·열린 이야기·최근 AI의 반응 방식·도움 거절·교정 선호를 중심으로 기존 문맥에 유지하며 매 턴 추가 LLM 호출은 하지 않는다. checkpoint에는 이 흐름을 보존한다.

평가는 연속된 대화 구간에서 구체적 기여, 맥락에 맞는 질문, 자연스러운 주제 유지·전환, 사용자 정정 반영, 요청하지 않은 학습 전환을 사람이 따로 판단한다. 요청 반영률·같은 요청을 다시 설명한 횟수·오해 복구 뒤 원래 주제로 돌아간 비율도 함께 본다. 질문 수·긍정 단어 수·통화 길이를 친구 같은 경험의 점수로 합치지 않는다. 친구 같은 느낌과 부담은 실제 사용자에게 별도로 확인한다. 대화 정책과 음향 정책은 별도 버전·플래그로 비교한다.

## 통화 시작 정책

### 선택 계약

서버의 순수 선택기 `opening-policy.ts`가 기존 `voice()` 준비 과정에서 시작 의도를 고른다. 문장을 고정된 목록에서 무작위로 바꾸는 방식으로 구현하지 않는다.

| 우선순위 | 조건 | 실행 |
| --- | --- | --- |
| 1 | 현재 통화에서 사용자가 이미 말하기 시작했거나 입력 commit을 기다리는 중 | 별도 오프닝을 생략하고 해당 발화에 답한다 |
| 2 | 같은 세션의 연결 복구·설정 갱신·checkpoint | 새로운 오프닝을 만들지 않는다 |
| 3 | 사용자가 준비한 주제가 있음 | `user_agenda`: 그 주제를 짧게 받아주고 사용자가 시작할 공간을 준다 |
| 4 | 최신 적격 통화에 관련 있는 비민감 사용자 근거가 있고 최근 같은 주제를 꺼내지 않음 | `supported_callback`: 근거 하나만 연결한다. 과거 계획의 실행·성공을 단정하지 않는다 |
| 5 | 적절한 회상 근거가 없음 | `brief_greeting` 또는 `open_invitation`: 짧게 인사하고 발언권을 주거나 질문 하나만 선택한다 |

사용자가 먼저 같은 주제를 재개하거나 이전 계획의 결과를 말하면 반복 제한보다 현재 의도를 우선한다. 첫 인사마다 질문·연습 제안·자기소개를 붙이지 않는다. 사용자가 단순히 인사를 돌려주면 짧은 응답만 하고 자기소개나 메뉴를 재시작하지 않는다. 새 주제를 억지로 만들어 다양성 수치를 높이지 않는다.

초기 제품 설정안은 같은 계정·캐릭터의 최근 5개 관찰된 시작을 최대 14일 범위에서 비교하고, 직전 2개 시작에서 같은 질문 의도·회상 주제를 재사용하지 않는 것이다. 자동 회상은 우선 7일 이내의 적격 근거로 제한한다. 이는 조정 가능한 제품 가설이며 최적값이 검증된 수치가 아니다. 더 오래된 유효한 기억은 사용자가 관련 주제를 꺼냈을 때 기존 기억 정책에 따라 사용할 수 있다.

`callback_eligible`와 `memory_ready`를 별도로 반환한다. `empty_handoff`, `source_pending`, `source_held`, `no_suitable_detail`, `topic_recently_used`, `source_stale`를 제한된 이유 코드로 구분한다. 최신 handoff가 비어 있으면 오래된 소재를 자동 회상으로 승격하지 않는다. 일반 대화 중 관련 기억 검색은 유지한다.

최근 assistant의 인사는 `style_context`로만 전달한다. 원문 전사에 있는 최근 시작을 제한된 길이로 읽되, 계정·캐릭터·제외·삭제 정책을 적용한다. 이 블록은 표현 반복 회피용이며 사용자 사실이나 교정의 근거가 될 수 없다. 사용자 사실은 계속 사용자 발화만 인용한다.

### 데이터와 API

시작 기능의 새 마이그레이션에 다음 두 테이블을 둔다. 주제·노출 이력은 다른 계정과 격리하고 동일 계정의 기기 간에는 공유한다. 실행 epoch와 응답 소유권은 각 통화에 한정하며, 세션 삭제 시 관련 이력을 함께 지운다.

```ts
type OpeningPlan = {
  id: UUID; session_id: UUID; user_id: UUID; companion_id: CompanionId;
  version: number; planner_version: string; prompt_version: string;
  memory_revision: number;
  source_session_id: UUID | null; source_version: string | null;
  evidence_ids: UUID[];
  mode: 'user_agenda' | 'supported_callback' | 'brief_greeting' | 'open_invitation';
  topic_key: string | null; opening_family: string; reason_code: string;
  created_at: string; request_deadline: string;
  authorization_state: 'offered' | 'claimed' | 'expired' | 'revoked';
};
type OpeningObservation = {
  event_id: UUID; plan_id: UUID; plan_version: number; attempt_id: UUID;
  stage: 'requested' | 'response_created' | 'text_generated'
    | 'playback_observed' | 'completed' | 'suppressed_by_user'
    | 'interrupted' | 'failed' | 'unknown';
  response_id: string | null;
  occurred_at: string; received_at: string; elapsed_ms: number;
  playback_state: 'playing' | 'blocked' | 'muted' | 'unknown';
  foreground: boolean | null;
};
```

`opening_plans`는 `(session_id, version)`을 고유하게 하고 세션당 활성 계획은 하나만 허용한다. `opening_observations`는 `event_id`를 고유하게 한다. `topic_key`는 제한된 주제 코드나 서버의 불투명한 thread 식별자이며 원문·이메일을 넣지 않는다. 최근 계획을 고른 것만으로 주제 사용 이력을 소비하지 않는다.

기존 `/coach/voice`의 `{sdp, clock, memory_context}`에 `opening_plan`을 선택 필드로 추가한다. 새 클라이언트는 `/coach/config`가 지원을 알린 경우에만 `openingProtocolVersion:1`을 전송한다. 이 필드가 없으면 서버는 기존 자동 VAD와 시작 정책을 유지한다. 구형 클라이언트에 `create_response:false`를 내려 이후 응답이 멈추는 호환성 문제를 막는다. 지원 버전·기능 플래그가 일치하는 새 경로에서만 계획을 실행한다.

일반적인 경우 계획과 사용 승인을 같은 `voice()` 준비 경로에서 처리해 추가 연결 왕복을 만들지 않는다. 이때 grant를 발급하고 계획을 `claimed`로 기록한다. 서버는 `opening_plan`과 함께 `{base_fingerprint, opening_instructions, user_reply_instructions}`를 반환한다. 두 지침은 서버가 안전·캐릭터·기억 경계와 제한된 style 문맥을 합성한 해당 통화의 지시문이다. 클라이언트는 검증된 묶음을 그대로 사용하며 별도 템플릿으로 기본 정책을 재구성하지 않는다. 전체 지시문을 관측·오류 로그에 남기지 않는다.

출처 revision·digest·hold·잊기·제외 상태를 발급 및 음성 문맥 전송 직전에 확인한다. 초기 승인 유효기간안은 2분이다. 만료 시 재승인은 아직 오프닝 요청을 한 번도 보내지 않은 계획에만 최대 한 번 허용한다. `requested` 또는 `unknown`인 실행은 재승인으로 재발화하지 않는다. 재승인 실패·계획 만료는 먼저 말할 권한에만 영향을 주며 사용자의 발화에 답할 권한을 막지 않는다. 같은 발언권 제어기가 정상 VAD 복원 ACK를 완료하거나, 사용자 commit에 수동으로 한 번 답한 뒤 정상 제어로 인계한다. 이미 전송된 문맥을 사후 취소로 회수할 수는 없으므로, 준비 이후의 출처 변경 감지와 응답 중단도 별도 경계 검사에 포함한다.

관찰 저장은 승인 계정·본인 세션·계획 version·허용 필드를 검증하는 `record_opening_observations` RPC로만 한다. 같은 `event_id` 재전송은 같은 ACK를 돌려준다. 늦은 관찰은 과거의 재생 정보를 보완할 수 있지만 만료된 발화 권한을 되살리지 않는다. 인증·출처 검증 실패는 구체적 회상을 차단하며, planner 자체 장애는 근거 없는 짧은 중립 인사 또는 사용자 선발화 대기로 처리한다.

### 클라이언트 실행과 관찰

`web/app.js`의 단순 `greeted` 대신 다음 실행 상태와 오프닝 응답 ID를 보관한다. 승인 계획의 실행 선점은 비동기 작업 전에 동기적으로 수행한다.

```text
offered → scheduled → requested → response_created
            ↓             ↓              ↓
     suppressed_by_user   unknown    playback_observed → completed
                                      ↓
                                  interrupted
```

실패·중단·생성·재생 관찰은 서로 다른 사실이므로 단일 최종 상태로 덮어쓰지 않는다. 살아 있는 통화 epoch 안에서는 시작 요청을 최대 한 번 보내고, 결과가 불명확한 요청을 자동으로 다시 발화하지 않는다. 브라우저 중단·네트워크 분할까지 포함한 전역 exactly once를 주장하지 않는다.

시작 전에는 `ready`, 입력 차단·답변 멈춤·발화 중·commit/전사 대기·기존 응답 여부를 함께 확인한다. 사용자 발화가 먼저 관찰되면 예약된 시작을 취소한다. 요청 후 사용자가 끼어들면 식별된 오프닝 응답만 취소하며, 사용자의 정상 응답을 포괄적인 `response.cancel`로 취소하지 않는다. 공급자 응답과 요청의 대응 관계를 확인하지 못하면 관찰을 `unknown`으로 남긴다.

최종 구현은 새 프로토콜의 `/coach/voice`가 공급자 세션을 최초부터 `create_response:false`로 만들고, 이를 기존 `voice-turn-controls.js`의 단일 발언권 제어에 합성한다. 해당 세션의 `session.created` 또는 정확히 일치하는 `session.updated`에서 유효 억제 설정을 확인하기 전에는 수동 시작 요청이나 정상 자동응답 복원을 하지 않는다. VAD의 음성 감지와 자동 commit은 유지하고 수동 commit은 추가하지 않는다. 현재 제어기는 자동 응답이 켜진 정책에서 초기화하므로, 신뢰된 정상 VAD 정책과 초기 억제 상태를 별도로 받는 초기화 API가 필요하다. 서로 독립된 두 컨트롤러가 같은 `session.update` 상태를 덮어쓰지 않게 한다.

미디어 준비 뒤 짧은 대기 동안 사용자 commit이 먼저 오면 그 입력에 대한 응답을 한 번 요청하고, 입력이 없으면 인사를 한 번 요청한다. 초기 실험값은 500ms이며 첫 응답 지연과 선발화 관찰로 조정한다. 시작 도중의 응답은 입력 item별로 소유권을 기록한다. 정상 자동 VAD로의 복원도 같은 제어기가 직렬 처리하며 `session.updated` ACK와 미해결 commit·응답을 함께 확인한 뒤 책임을 넘긴다. 전이 중 입력을 두 번 처리하거나 유실하지 않는 공급자 이벤트 순서를 계약·실제 음성 검사로 확인하기 전에는 이 경로를 공개 활성화하지 않는다. 시작을 다듬기 위해 마이크를 끄지는 않는다.

음성 시작 이벤트가 늦게 도착하면 인사 일부가 시작될 가능성은 남는다. 이때는 식별된 오프닝만 중단하고 사용자 입력을 보존한다. 기존 `create_response:true`에 조건 검사만 붙인 대안은 자동 응답과 인사가 동시에 생성될 수 있으므로 최종 경합 방지책으로 채택하지 않는다.

기본 세션 지침에서 무조건 첫 인사를 하라는 규칙을 제거하고, 오프닝 의도는 해당 `response.create`의 한 번짜리 지시로만 합성한다. 한 번짜리 지시가 세션 지침을 대체할 수 있으므로 안전·영어 응답·캐릭터·기억 경계를 포함한 전체 기본 지침을 유지하는 공통 합성 함수를 사용한다. 자동 VAD가 먼저 답하는 경우에도 사용자 입력에 직접 답하고 별도 인사를 덧붙이지 않는 정책을 적용한다.

`response.done`은 생성 완료, `output_audio_buffer.started`는 공급자 출력 시작이다. 둘 다 사람이 들었다는 증거가 아니다. 오프닝 응답과의 대응이 확인되고 브라우저의 `play()` 성공·재생 진행·음소거 아님이 함께 관찰될 때 `playback_observed`로 기록한다. 대응이 모호하면 `unknown`이다. 텍스트만 생성된 응답은 음성 노출이 아니다. 백그라운드 탭에서도 재생될 수 있으므로 `foreground=false`를 실패로 단정하지 않는다.

주제 사용 제한은 `playback_observed`를 노출 대리값으로 삼으며 실패한 연결·미재생 계획은 장기 이력을 소비하지 않는다. 계획한 `opening_family`와 실제 생성 문장의 분류를 별도로 평가한다. 계획이 다양했다는 사실만으로 실제 시작이 다양해졌다고 보고하지 않는다.

## 대화 의도와 불확실성 처리

### 통화 중 응답

| 의도 | 우선 행동 | 피할 행동 |
| --- | --- | --- |
| `conversation` | 마지막 구체적 내용에 반응하고 발언권 반환 | 매번 질문·수업으로 전환 |
| `language_help` | 요청한 표현이나 설명을 바로 제공 | 답을 주기 전 강제 추측·반복 |
| `conversation_control` | 짧게 수용하고 길이·교정·기다리기 요구를 반영 | 요청 자체의 영어를 교정 |
| `app_issue` | 문제를 짧게 확인하고 실제 확인 가능한 상태·조작으로 안내 | 확인되지 않은 기술 원인 설명, 문법 예문으로 전환 |
| `unclear` | 문제가 되는 부분 하나만 짧게 확인 | 불명확한 뜻을 사실로 확정 |

이 구분은 MVP에서 Realtime 지침과 회귀 평가 기준으로 사용하며 매 턴 외부 분류 API를 호출하지 않는다. 속도 변경은 기존 UI와 ACK가 있는 제어 경로가 담당한다. 현재 소스에는 멈춤·재개 모듈이 있으나 사용자 UI 바인딩은 없으므로 기존 버튼이 있다고 전제하지 않는다. 필요할 때 같은 제어기에 명시적 중단 동선을 연결한다. 모델이 말을 멈추겠다고 한 것과 실제 제어 성공을 구분한다. 자연어 교정 선호는 우선 현재 통화의 응답 정책으로 적용하고, 지속 설정은 추론만으로 계정 프로필에 기록하지 않는다. 추후 음성 명령을 도구와 연결할 때는 제한된 명령·실행 결과·ACK를 별도로 설계한다.

같은 오해에 사용자가 다시 반박하면 이전 해석을 반복하지 않고 확인 질문으로 전환한다. 길이를 줄여 달라는 요청은 다음 응답부터 반영한다. 앱 오류 설명이나 도움 거절을 요청 없이 학습 예문으로 바꾸지 않는다. 사용자가 그 내용을 영어로 표현해 달라고 명시하면 표현 도움으로 처리한다. 합성 평가 예: 사용자가 “교정은 요청할 때만 해 줘”라고 하면 짧게 수용하고 대화를 이어가며 그 문장을 교정 목록에 넣지 않는다.

### 사후 분석 계약

원문 `transcript_events`는 보존하고, 나중 설명이나 개선문으로 덮어쓰지 않는다. 새 분석의 `analyses.content`는 `schema_version:2`와 항목별 근거 상태를 가진다. 분석·기억에 공통으로 적용할 보류 기록은 별도 `evidence_resolutions`에 둔다.

```ts
type Grounding = {
  status: 'supported' | 'unclear_transcription' | 'unclear_intent';
  evidence_ids: UUID[];       // 사용자 발화 1~12개
  context_event_ids: UUID[]; // 같은 통화의 앞뒤 문맥 최대 6개
  reason_code: 'NONE' | 'ASR_SUSPECTED' | 'INTENT_CONFLICT'
    | 'FRAGMENT_WITHOUT_CONTEXT';
};
type SummaryClaim = { text: string; grounding: Grounding };
type Omission = {
  evidence_ids: UUID[];
  status: 'unclear_transcription' | 'unclear_intent';
  reason_code: Grounding['reason_code'];
};
```

`supported`는 전사와 문맥이 해석을 지지한다는 모델 판단이며 원음 확인을 뜻하지 않는다. 서버는 화자·계정·통화·인용 원문·digest·상태 전이를 검증할 수 있지만 의미적 타당성을 자동 보증할 수는 없다. 문맥에는 assistant 발화가 포함될 수 있어도 사용자 사실과 교정 원문의 근거는 사용자 발화로 제한한다.

불확실한 후보는 `error`를 `alternative`로 낮추는 대신 노출 대상에서 제외한다. 보류 목록에는 근거와 이유 코드만 남기며 추측한 개선문·사실은 저장하지 않는다. 유효한 후보에만 기존 `error | alternative`를 적용한다. 구어로 가능한 표현을 더 격식 있는 표현으로 바꾼 것은 오류로 단정하지 않는다.

요약은 자유문 하나를 별도로 생성하지 않고 `summary_claims` 중 통과한 조각으로 기존 표시용 `summary`를 구성한다. 교정·강점·practice·다음 시나리오·기억 사실에도 같은 근거 정책을 적용한다. 항목 수를 채우기 위해 불확실한 후보를 보충하지 않으며, 표현이 겹치는 교정과 연습은 하나의 학습 항목으로 연결한다.

사용자 이의는 기존 `learning_source_holds`, 별도 의도 설명과 수락은 `learning_reviews`를 사용한다. 모델이 `user_clarified`나 사용자 확인 완료를 스스로 생성할 수 없다. 재검토 결과는 원문 버전과 연결하고 새 사용자 설명을 원래 발화처럼 인용하지 않는다. 현재 보류 로직은 항목 단위가 있으므로 `item_id=null` 행 하나만 넣고 모든 소비자가 차단됐다고 가정하지 않는다.

학습 분석과 handoff 생성은 계속 독립적으로 수행하되, 공통 보류 guard를 생성 전·결과 저장·조회·다음 통화 전송에 적용한다. 신규 `evidence_resolutions`의 계약은 다음과 같다.

```ts
type EvidenceResolution = {
  id: UUID; case_id: UUID; revision: number;
  user_id: UUID; session_id: UUID; evidence_ids: UUID[];
  evidence_digest: string; // 대상 발화의 ID·원문 digest
  assessed_transcript_digest: string; // 판단 당시 전체 문맥 버전
  origin: 'model_assessment' | 'user_dispute' | 'user_clarification';
  producer_key: string; // job/review ID에 연결된 멱등 키
  state: 'open' | 'clarified' | 'withdrawn';
  reason_code: 'ASR_SUSPECTED' | 'INTENT_CONFLICT'
    | 'FRAGMENT_WITHOUT_CONTEXT' | 'USER_DISPUTED';
  clarification_review_id: UUID | null;
  clarification_event_ids: UUID[];
  created_at: string;
};
```

모델은 불확실성을 `open`으로만 추가할 수 있다. `supported`라는 다른 모델 출력이 열린 보류를 해제하지 못한다. 해제는 원문 변경으로 해당 근거 버전이 달라지거나, 연결된 사용자 설명/발화로 재검토를 완료한 경우에만 허용한다. 사용자는 자신의 이의를 명시적으로 철회할 수 있으며, 모델은 이를 대신 생성할 수 없다. `clarified`는 유효한 사용자 설명 또는 발화 근거가 필수다. 단순히 새 발화가 추가돼 전체 통화 digest가 바뀌어도 대상 원문이 같으면 열린 보류를 잃지 않는다. 보류된 부분 이외의 명확한 주장은 계속 사용할 수 있다.

기존 `learning_source_holds`와 새 기록을 합친 공통 유효성 조회 함수를 만든다. 기존의 항목별 의도 보류도 `learning_sources.evidence_ids`로 풀어 해당 해석을 사용하는 모든 파생 자료에 적용한다. 항목이 생성되기 전의 자동 보류와 세션/발화 단위 보류도 같은 함수가 처리한다. 공개 클라이언트가 모델 판정이나 사용자 확인을 임의로 쓰지 못하도록 서버 전용 쓰기와 기존 사용자 재검토 RPC를 구분한다.

각 생성기는 발견한 보류를 자신의 결과와 같은 저장 트랜잭션에서 등록한다. 등록 시 해당 계정·캐릭터의 근거 상태 revision을 올리고, 영향받는 요약 조각·교정·practice·handoff·주간 결과와 캐시를 무효화한다. 다른 생성기의 이미 완료된 결과도 조회 시 필터링하며 진행 중 결과는 이전 revision으로 게시할 수 없다. 관련 없는 근거의 결과까지 통째로 버리지 않도록 항목별 의존 ID를 보존한다.

이 guard는 **이미 발견되거나 사용자가 표시한 불확실성**의 우회 유입을 막는다. 두 생성기가 모두 뜻을 잘못 확신하거나 다른 생성기가 보류를 발견하기 전에 이미 전달한 내용까지 소급 방지하지는 못한다. 의미 품질과 보류 발견 시점은 별도로 평가하고, 상태 변경 후에는 재노출을 차단한다. 분석 완료를 기다려야 기억을 생성하도록 묶지는 않는다.

기존 분석은 `legacy_unassessed`로 읽기를 유지한다. 과거 노트를 일괄 덮어쓰지 않으며 재처리는 명시적 작업으로 수행한다. 캐시와 저장 guard에는 원문 digest, grounding 정책·schema 버전, 기억 revision·보류 상태를 포함해 늦은 결과가 이미 보류된 해석을 되살리지 못하게 한다. `analysisSchema`·`validateAnalysis`뿐 아니라 `mergeAnalyses`·`sourceIds`·SQL materializer를 함께 갱신한다. 긴 통화의 chunk 병합에서 근거 상태나 보류 항목이 유실되거나 assistant 문맥이 사용자 근거로 승격되지 않게 한다.

## 스피커폰의 소음 중단

사용자가 확인한 환경은 휴대폰 스피커폰이다. 현재 `getUserMedia()`는 `echoCancellation:true`, `noiseSuppression:true`를 요청하며 AGC는 지정하지 않는다. 요청과 실효 적용·음향 효과는 다르다. 공급자 설정은 `semantic_vad`, `eagerness:low`, `interrupt_response:true`이고 입력 `noise_reduction`은 명시하지 않는다. 현재 유효 세션 값을 확인하지 않았으므로 필터가 꺼졌다고 단정하지 않는다.

평상시 `speech_started` 처리는 상태 표시를 바꾸며 로컬 취소를 보내지는 않는다. 현재 앱에서 floor의 hold/resume 호출은 연결돼 있지 않고 직접적인 `response.cancel`은 종료 경로에 있다. 시각화 분석기도 오디오 출력에 연결돼 있지 않다. 따라서 스피커 출력 재유입이나 주변 소리를 발화 시작으로 잘못 감지한 뒤 공급자가 자동으로 중단하는 경로가 우선 가설이다. 실제 타임라인 없이 이번 VOC의 원인으로 확정하지 않는다.

`eagerness:low`는 주로 말끝을 기다리는 정책이며 작은 입력의 시작 민감도를 낮추는 값이 아니다. `interrupt_response:true`에서 공급자가 먼저 취소하면 브라우저가 `speech_started`를 받은 뒤 잠깐 기다리는 처리만으로 그 취소를 막을 수 없다. [공식 VAD 안내](https://developers.openai.com/api/docs/guides/realtime-vad)와 [자동 중단 명세](https://developers.openai.com/api/reference/resources/realtime/client-events)를 기준으로 한다.

### 첫 적용 후보

스피커폰을 대상으로 `audio.input.noise_reduction:{type:'far_field'}`를 명시한 후보를 비교한다. 이 필터는 VAD 이전에 적용되며 원거리 마이크에 맞춘 처리다. 휴대폰 스피커폰에서 효과가 있다는 보장은 아니며 에코 제거의 대체재도 아니다. 이어폰은 별도의 근거리 후보로 분리한다. 브라우저 종류만 보고 출력 경로를 확정하지 않는다. [입력 처리 명세](https://developers.openai.com/api/reference/resources/realtime/subresources/calls/methods/create)

```ts
// 스피커폰 검증 후보. 아직 운영에 적용한 설정이 아니다.
audio.input = {
  noise_reduction: { type: 'far_field' },
  transcription: { model: 'gpt-realtime-whisper', delay: 'medium' },
  turn_detection: {
    type: 'semantic_vad', eagerness: 'low',
    create_response: true, interrupt_response: true
  }
};
```

이 단계에서는 정상적인 끼어들기를 유지한다. 시작 프로토콜을 함께 쓰면 시작 구간만 앞서 정의한 `create_response:false`를 합성하고, 정상 통화의 유효 정책과 혼동하지 않는다. `session.created/updated`의 실제 필터·VAD 설정을 확인하며, 미지원·거절을 적용 성공으로 기록하지 않는다. 필터 설정 거절은 설정 실패로 처리하고 허용된 이전 정책으로 한 번 복구하거나 해당 기능을 비활성화한다. 음성 연결 불안정 안내나 전사 실패로 오분류하지 않는다.

브라우저는 `getSupportedConstraints()`와 track `getSettings()`에서 AEC·NS·AGC의 지원·실효 boolean만 제한적으로 확인한다. 값이 없으면 `unknown`으로 둔다. 스피커·이어폰·Bluetooth 전환 뒤 재관측하며 장치 ID·이름·원음은 진단에 넣지 않는다. `autoGainControl:false`나 필터 강도 변경은 별도 비교 후보이며 작은 실제 목소리 손실을 확인하기 전 전역 기본값으로 채택하지 않는다.

### 중단 타임라인과 후속 제어

오류 진단과 별개로 response별 `speech_started`, 로컬 cancel/clear 요청, `response.done` 상태, 출력 started/stopped/cleared와 유효 VAD 정책을 제한된 이벤트로 연결한다. 원문 없이 경과 시간·응답 키 hash·동작 이유 코드만 저장하고, 진단의 10초 중복 억제를 그대로 적용해 시간 관계를 잃지 않게 한다. `provider_auto`, `client_cancel`, `output_clear`, `transport_lost`, `unattributed`를 구분하며 근거가 없으면 마지막 범주로 남긴다. 자동 중단으로 분류돼도 소음이었는지 정상 끼어들기였는지는 별도 관찰이 필요하다. 상태 그림이 듣기로 바뀐 것과 실제 오디오가 멈춘 것도 구분한다.

필터 이후에도 문제가 남으면 별도 플래그에서 실제 발화 확인 후 중단하는 제어를 실험한다. 자동 중단을 끈 뒤 기존 floor가 입력 item별 응답 책임·생성·취소·출력 clear ACK·정상 VAD 복원을 모두 담당해야 한다. 단순히 `interrupt_response:false`만 바꾸면 실제 사용자의 중단 요청이 작동하지 않거나 기존 응답 중 새 답변이 생성되지 않을 수 있다. AI 발화 중 마이크를 끄거나 사용자 입력을 버리는 방식은 채택하지 않는다.

이 후속 제어의 발화 판별은 시각화용 음량 임계값이나 지속 시간만으로 구현하지 않는다. 짧은 “stop/wait”, 작은 실제 음성, 맞장구, 멀리 있는 사람의 말, AI 음성의 에코를 구분해야 한다. 로컬 음성 판별기를 도입한다면 모바일 CPU·지연·배터리와 오탐도 검증한다. 확인되지 않은 후보 입력은 삭제하지 않으며, 명시적 중단 동선을 연결해 사용자가 언제든 제어할 수 있게 한다. `server_vad`의 threshold를 semantic VAD에 섞지 않는다.

### 실기기 검증

같은 휴대폰에서 스피커폰·이어폰, 출력 음량·거리, 조용한 방·팬·책상 접촉·옷 마찰·멀리 있는 대화를 비교한다. 잡음 때 멈추지 않는지와 함께 조용한 실제 발화·첫 음절·짧은 중단 요청이 보존되는지, 의도한 끼어들기 지연이 늘지 않는지를 확인한다. iOS Safari와 Android Chrome, 오디오 경로 전환도 포함한다. AEC/NS와 추가 필터를 함께 적용해 실제 발화가 약해지는 반례를 확인한다. 원본 녹음 없는 현장 관찰도 가능하며 추가 녹음을 기본 수집하지 않는다.

설정 경로·ACK·중단 이벤트를 검사하는 mock 테스트와 실제 음향 효과를 나눠 보고한다. 실기기 비교를 마치기 전에는 필터 후보를 소음 문제 해결로 발표하지 않는다.

## 관측과 성능 설계

| 영역 | 최소 변경 | 지표와 의미 |
| --- | --- | --- |
| 요청 오류 | 기존 `sendRealtime`의 event ID 연계를 유지. 미등록·ID 없음·만료를 구분하고 pending 항목 보호 | `unknown`을 마지막 요청으로 추측하지 않음. 코드·요청 종류·연계 가능 비율 집계 |
| 분석 단계 | 시도별 `generated`, `validated`, `persisted`, `exposed` 시각·결과 코드 | 모델 생성 성공과 사용자에게 유효한 결과 제공을 구분 |
| 처리 지연 | task의 첫 준비 시각을 원문 버전별로 보존. 기존 exposure 기록 재사용 | 종료→노트·handoff 준비 P50/P95. 재확인의 `updated_at`과 백필을 제외 |
| 실시간 사용량 | `response.done` usage를 내용 없이 응답 ID로 중복 제거해 합산 | 수집률과 음성 포함 추정 비용/통화분. 클라이언트 수치로 비용 승인하지 않음 |
| checkpoint | 전체 학습 노트 대신 작은 전용 스키마 사용 | 입력 정지 시간·정리 성공·사실/미해결 주제 보존을 함께 확인 |
| 기억 조회 | 계정·캐릭터·revision별 singleflight와 짧은 캐시 | 화면 진입당 HTTP 수·중복 수·기록 표시 지연 |

기존 진단 allowlist에 원문 오류 메시지·전사·SDP를 추가하지 않는다. 연계 사유·단계·usage는 각각 제한된 구조로 저장한다. 현재도 모든 `sendRealtime` 요청에 ID를 붙이므로 이를 새로 구현하는 계획으로 잡지 않는다. 오류의 ID가 없으면 특정 요청 탓으로 돌리지 않는다.

`model_spend.outcome=generated`의 뜻은 바꾸지 않고 `validation_status: pending|valid|invalid|not_applicable`, `validated_at`, 제한된 `validation_code`를 추가한다. `artifact_type`, `artifact_id`, `persisted_at`은 결과 저장 트랜잭션에서 연결하며 chunk 결과를 최종 노트와 구분한다. 노출에는 기존 `learning_feedback.exposed_at`을 재사용한다. `post_call_tasks.first_ready_at`은 `kind + source_version + memory_revision + policy/request_key`의 `ready_version`별 최초 서버 시각으로 기록하고 재확인 때 덮어쓰지 않는다. 근거 없는 과거 시각은 null로 둔다.

실시간 사용량은 진단 상한·중복 억제와 분리한 `realtime_response_usage`에 `(session_id, response_key_hash)` 고유 키로 저장한다. `response.created`의 관측 분모와 `response.done`의 실제 usage 수신을 구분하고 취소·실패도 포함한다. 전체·텍스트·오디오·캐시 토큰은 제공되지 않은 값을 0으로 만들지 않고 null로 둔다. 모델·정책 버전은 서버 voice job에서 채운다. 수집률은 관측된 응답 중 usage가 수신된 비율이며, 전혀 관측하지 못한 응답까지 포함하는 완전성 지표로 해석하지 않는다.

checkpoint 초기 출력안은 `summary` 최대 900자, `open_threads` 최대 3개, `current_preferences`와 `uncertain_details` 각 최대 3개, `evidence_ids`이며 출력 한도를 별도로 둔다. 현재 주제·사용자 제어 요청·계획과 결과의 구분을 보존한다. 분석을 작게 바꿔도 서버 호출을 기다리는 동안의 입력 정지 자체가 사라지지는 않는다. 10분 고정 정리는 다시 도입하지 않는다. 기존 18,000 입력 토큰 또는 실제 한도 오류 조건과 ACK·부분 삭제·실패 복구를 유지한다.

기억 snapshot은 `scope + companion_id + operation + representation`별 진행 중 Promise를 공유하고 초기 TTL은 15초안으로 둔다. 항목에는 `generation`, 기억 revision, 원문 `source_version`을 함께 저장한다. 기억 revision만으로 원문 추가를 모두 감지한다고 가정하지 않는다. 다른 캐릭터의 준비 확인은 필요할 때만 요청한다. 기억 수정·삭제·잊기·보류·새 통화 저장·계정 전환 즉시 캐시와 진행 중 결과를 무효화한다. 늦은 응답의 generation이 다르면 UI 반영과 재캐싱을 모두 금지한다. 화면 캐시는 통화에 기억을 전송하기 직전의 서버 검증을 대체하지 않는다.

원문과 중복되지 않는 운영 진단·시작 관찰의 보존 기간은 초기 30일안을 두고 TTL 작업·삭제 검증을 함께 구현한다. 열린 근거 보류는 이 TTL로 지우지 않으며 원문/계정 삭제나 명시적 해제 수명을 따른다. 계정/세션 삭제 cascade와 본인 계정 접근을 유지한다. 실제 음성 품질 평가에 필요한 녹음은 기존 로그와 별개의 동의·보존 범위로 다루며 기본 수집을 늘리지 않는다.

## 평가와 출시 조건

출처 연결 검사와 의미 품질 검사를 나눈다. 현재 51항목의 근거 연결과 교정 원문 19개의 부분 문자열 검사는 통과했지만 의도 보존을 보증하지 않는다. 재검토 후보 5개는 오교정률로 쓰지 않는다. 실제 자료를 평가할 때 원문 버전과 접근 범위를 보존하며, 저장소 테스트에는 개인 대화 원문 대신 합성 반례를 넣는다.

| 평가 묶음 | 필수 사례 |
| --- | --- |
| 오프닝 실행 | RTC/DC 중복 콜백, 같은 통화 재연결, 사용자 선발화·commit 대기·출력 직전 끼어들기, 답변 멈춤/재개, 속도 갱신, checkpoint, 종료 |
| 이력과 기억 | 미재생·텍스트만 생성·재생 차단, 늦은 receipt·만료, 다른 계정/캐릭터, 발급 후 보류/잊기, 빈 최신 handoff, 오래된 계획의 결과 단정 금지 |
| 의도와 교정 | 앱 불만·교정 거절·짧게 말해 달라는 요청, 문맥 충돌, 명확한 표현 요청, 유효 구어의 대안, 한글·혼합 입력, 근거 없는 사실 추출 |
| 파생 정보 | 보류 해석이 요약·practice·handoff·주간 분석으로 우회 유입되지 않음, 사용자 설명과 원문 구분, 보류 뒤 늦게 완료된 결과 차단 |
| 운영 | 진단 거절이 통화/저장 상태를 오염시키지 않음, 캐시 무효화, 분석 재시도와 실제 준비 시각, 정리 후 문맥/입력 복구 |

오프닝은 완전 문장 반복뿐 아니라 같은 질문 의도·주제의 연속 반복, 불필요한 재시작, 첫 의미 있는 사용자 발화까지의 시간, 시작 전후 끼어들기·거절을 본다. 최초 발화 시간은 speech 이벤트가 있는 표본에서만 계산하고 전사 수신 시간으로 음성 지연을 대신하지 않는다. 사용자 주도 대화를 짧게 끝낸 것을 실패로 세지 않는다.

사후 품질은 의미 보존·교정 필요성·대안 분류·불확실성 보류의 적절성과 정상 후보 누락을 함께 검토한다. 지연 회상은 1·3·7일 관찰창이 성숙한 대상만 평가하고, 다음 통화의 자발적 사용은 예문 반복·힌트 후 사용·새 상황 사용을 구분한다. 표현 출현이나 노트 열람을 숙달로 표시하지 않는다. 기존 [평가 절차](enhancement-evaluation-protocol.md)의 사람 라벨·관찰창 계약을 유지한다.

출시는 추가형 DB migration → 구형 클라이언트 호환 서버와 capability 제공 → 새 클라이언트 배포 순서다. 기능 활성화는 합성 회귀 → 보호된 실제 전사의 오프라인 검토 → 시작 계획만 계산하는 shadow 모드 → 소규모 실제 음성 확인 → 확대 순서로 한다. 동일 입력·모델·음성·속도·기억을 고정해 새 정책을 비교한다. 현재 규모에서는 계정별 층화 결과와 사례를 보고하며 통계적 향상률을 주장하지 않는다. 품질 목표치는 추가 기준 표본을 확보한 뒤 정한다.

계정 간 정보 혼입·잊기/보류 위반·사용자 기록 손실은 한 건이라도 확대를 중단한다. 시작 다양성 때문에 첫 응답 지연·사용자 발화 취소·불필요한 질문이 늘면 기본 짧은 시작 전략으로 되돌린다. 새 시작 기능과 grounding 정책은 별도 플래그로 되돌릴 수 있게 하며, 기존 통화 저장·신뢰성 수정은 유지한다.
