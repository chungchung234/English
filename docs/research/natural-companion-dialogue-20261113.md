# 친근한 음성 대화 고도화 연구와 실행 설계

검토일: 2026-11-13 KST. 검토 소스: `9b3eb24535ec2ce55a4152aa1635009719b6cf08`. 공개 앱 기준: `ef11416d7ffc556d2b6aa209d002f5adf441fd2e`.

[제품 목적](phone-english-purpose.md)이 상위 기준이다. 통화 자체가 친근한 캐릭터 대화이며, 학습은 통화 뒤 실제 원문을 바탕으로 선택한다. 아래 설계는 후보이며 구현·효과 검증이 끝난 기능이 아니다. 이번 조사는 코드·기존 합성 출력·1차 문헌과 운영 메타데이터 집계를 사용했다. 새 유료 생성, 앱 변경, 배포는 수행하지 않았다.

## 권고

**먼저 실제 요청 경로와 지침 적용을 확인하고, 캐릭터의 관점과 함께 나눈 대화 상태를 보강한 뒤, 내용 생성과 음성 표현을 분리하는 후보를 비교한다.** 문구를 추가한 만큼 효과가 있다는 가정이나 모델 가격에 따른 자동 승격을 하지 않는다.

| 순서 | 구체적으로 할 일 | 다음 단계로 갈 근거 |
| --- | --- | --- |
| 1 | 공개 빌드·클라이언트 capability·요청의 turn-control·서버 적용 정책을 대조. 지침의 승인 버전과 provider 관측 상태를 분리 | 의도한 경로·지침으로 실제 응답을 요청했다는 증거 |
| 2 | 캐릭터가 가진 관점과 사용자 사실을 구분하고, 실제 양쪽 발화가 있는 대화 교환 기록 추가 | 같은 소재에서 관점이 유지되고, 재접속해도 실제 이전 이야기를 자연스럽게 이어감 |
| 3 | 간결한 현재 대화 자료와 상황별 다중 턴 예시를 비교 | 새 사례에서 메뉴·과잉긍정이 줄고 따뜻함·명시 요청 대응이 보존됨 |
| 4 | 개선이 부족하면 텍스트 대화 작성기→음성 합성과 GPT-Live를 별도 비교 | 내용 제어·음성 자연스러움의 이득이 지연·중단 제어·비용 손실을 상쇄함 |

## 1. 현재 증거와 아직 모르는 것

### 운영 요청 경로

2026-11-13 **22:43 KST**에 최근 24시간의 `analysis_jobs` 메타데이터를 읽기 전용으로 집계했다. 사용자 ID·이메일·대화 원문·음성은 가져오지 않았다. 원인 후보를 좁히면서 turn-control과 빌드 분류를 추가해 총 세 번 조회했으며, [최종 집계](natural-companion-metadata-20261113.json)를 보존했다.

- 완료된 음성 **연결 준비 작업** 2건이 현재 v4 서버 정책을 사용했다.
- 2건 모두 `turn_control=provider_vad`이고, `opening_context_kind/reason`은 허용된 enum으로 기록되지 않았다. 집계의 `absent_or_other`는 누락과 기타 값을 구분하지 않는다.
- 2건 모두 현재 공개 릴리스와 다른 비어 있지 않은 `client_build`를 기록했다. 실제 빌드 값은 보고서에 수집하지 않았다.
- 이 수치는 실통화 수·사용자 수·품질 실패 수가 아니다. SDP 교환 성공만으로 실제 연결·청취를 확인할 수 없다. 이 두 건이 VOC의 통화였는지도 모른다.

서버는 요청에 `turnControl:'manual_turns_v1'`이 있을 때만 별도 opening 자료와 qualified-turn 경로를 준비한다. 필드가 없으면 호환용 provider VAD 경로이고 opening metadata가 없는 것이 코드상 정상이다. 따라서 위 두 건을 새 opening 정책의 사용 실패율로 계산할 수 없다. 현재 새 클라이언트는 `/config`의 capability를 성공적으로 받은 뒤 화면에 진입하므로, 단순한 config 조회 실패가 조용한 호환 경로 진입을 일으킨다고 단정해서도 안 된다. 구형/다른 JS, 직접 API 요청, 업그레이드 전에 설정을 받은 오래 열린 탭 등을 구분할 기록이 필요하다.

**첫 실행 과제:** 새 통화 직전에 빌드·capability·선택 경로를 대조하고, 서버가 실제 적용한 모드를 응답과 job에 연결한다. 오래 열린 탭의 갱신은 통화 종료 뒤 처리한다. 통화 중 강제 새로고침이나 반복 오류 팝업으로 해결하지 않는다. 현재 공개본과 같은 지침을 쓴 WS 합성 생성에서도 메뉴식 시작은 관찰됐으므로 버전 정합만으로 말투까지 해결된다는 뜻은 아니다. 공개 브라우저의 기존 검사는 provider 전송을 모의한 별도 검사였다.

## 3. 지침 적용을 먼저 검증하는 설계

[공식 Realtime API](https://developers.openai.com/api/reference/resources/realtime/client-events)는 response별 지침이 session 지침을 대체할 수 있고, 지침 준수를 보장하지 않는다고 명시한다. [세션 문서](https://developers.openai.com/api/docs/guides/realtime-conversations)는 설정 갱신 뒤 `session.updated`에서 새 상태를 확인하도록 설명한다. 따라서 다음 세 증거를 나눈다.

1. **전송:** backend가 승인한 지침을 요청에 실었는가.
2. **설정:** provider가 돌려준 설정과 기대한 설정이 일치하는가.
3. **행동:** 그 경로에서 간단한 합성 지침이 실제 생성에 반영되는가.

자연스러움은 이 셋 이후의 별도 평가다.

권장 상태는 `authoritativeInstructions={policyVersion, memoryRevision, contextGeneration, digest, text}`와 `observedProviderState`의 분리다. `session.created`의 초기 설정이나 속도/floor 갱신 응답이 승인 지침을 덮어쓰지 않게 한다. checkpoint 갱신은 직렬 대기열의 현재 요청과 정확한 내용·digest가 맞을 때만 새 기준으로 채택한다. provider가 반영하지 않는 임의의 metadata/event ID를 ACK 상관 키로 가정하지 않는다. 현재도 유효한 memory revision의 승인 지침을 유지하고 불일치를 진단하며, 새 연결 종료·반복 팝업을 추가하지 않는다. 잊기·제외로 옛 지침이 무효화됐으면 재사용하지 않고 최신 승인된 기억 없는 구성으로 전환한다. 검증되지 않은 과거 기억을 복원해 가용성을 확보하지 않는다.

먼저 로컬 모의 사건으로 초기 기본값, 속도-only ACK, 늦은 ACK, checkpoint 뒤 옛 ACK를 재현한다. 그 뒤 필요할 때만 고정 합성 진단 6회(session 지침만 / 다른 response override / 속도 변경 후, 각 2회)를 사용한다. 서로 다른 무해한 표식 문장으로 어느 경로가 유효한지 확인한다. 표식은 격리된 평가 세션에만 사용한다. 6회는 경로를 가르는 개발 예산이며 통계적 표본 근거가 아니다. 전체 지침에서도 같은 대조가 필요한지 앞 결과로 결정한다.

| 대화 교환 기록 | 실제 양쪽 발화, 날짜, source revision, 재생 상태가 있는 이야기 | 함께 무엇을 말했는지에 대한 과거 자료. 미래에 수행할 지시가 아님 |
| 현재 통화 상태 | 현재 사용자 발화 또는 null, 방금 주고받은 내용, 정정·거절·미완료 화제 | 지금 무엇에 응답하는지. 오래된 질문을 현재 질문으로 승격하지 않음 |
| 사후 학습 | 원문 기반 교정·선택 복습·관찰 | live 대화 자료와 분리 유지 |

캐릭터에는 ‘따뜻하다’뿐 아니라 무엇을 왜 좋아하는지, 어떤 조건에서는 다른 선택을 할 수 있는지가 필요하다. 사용자의 취향을 거울처럼 따라가는 것과 대화상 이유로 관점을 조정하는 것을 구분한다. 늘 반대하거나 매 턴 자기 의견을 말하는 규칙을 만들지 않는다. 실제로 하지 않은 하루·인간 이력·배타적 관계는 추가하지 않는다.

### 대화 교환 기록의 최소 계약

예상 필드는 `source_session_id`, `source_revision`, `companion_id`, `topic`, `status`, `occurred_at`, `source_time_zone`, `caller_utterance_refs`, `companion_utterance_refs`, `unresolved_exchange`다. 각 발화 참조에는 정확한 원문, event ID, speaker가 있다. 상태는 계획·결과·미상과 열린/종료 교환을 구분한다. `unresolved_exchange`는 과거 교환의 서술이며 ‘다음에 반드시 물어라’ 같은 실행 지시를 받지 않는다.

AI 발언은 **AI가 그 말을 했다는 근거**이며 사용자 사실의 근거가 아니다. 생성 완료만으로 함께 들은 이야기라고 간주하지 않는다. assistant 자료는 client의 실제 재생 완료와 취소 상태가 연결된 것부터 사용하고, `playback_completed`도 사람이 들었다는 물리적 증명과 구분한다. 이 연결이 없는 예전 자료를 재생된 공유 기억으로 소급하지 않는다.

양쪽 발화가 있는 새 기록에도 계정·캐릭터 소유권, source revision, 제외·잊기·현재 정정·날짜 검증을 적용한다. 사용자가 지운 정보가 AI의 재진술을 통해 되살아나지 않게 연결된 교환 전체를 무효화한다. 현재의 사용자 근거 검증을 완화하거나 옛 feedback summary·학습용 `follow_up`을 다시 live에 넣는 방식으로 확장하지 않는다.

### 시작과 후속 응답에 필요한 자료만 조립한다

시작에는 `caller_utterance:null`, 접속 상태, 관련 있을 수 있는 실제 과거 교환과 캐릭터 관점을 제공한다. 현재의 ‘최신 handoff 하나에서 첫 적합 thread’만 보는 선택과, 여러 적격 교환 중 아직 의미 있는 이야기를 고르는 선택을 비교한다. 최신 통화가 짧다는 이유만으로 그전의 열린 이야기를 잃지 않게 하되, 잊기·제외·시점 검증은 동일하게 적용한다.

후속 응답에는 현재 뜻, 방금 교환, 필요한 과거 자료를 구분해 넣는다. 예시도 상황에 맞는 다중 턴을 비교한다: 평범한 공유에 반응하기, 다른 취향을 주고받기, 조언을 거절하면 실제로 행동 바꾸기, 표현을 알려준 뒤 원래 이야기로 돌아가기. 긴 문장을 짧게 자른 결과나 ‘공감→질문’ 고정 템플릿을 좋은 예시로 삼지 않는다. 사례는 개발용/holdout으로 나누며 평가 발화를 그대로 프롬프트에 복사하지 않는다.

## 5. 생성 구조 선택

[공식 voice architecture 문서](https://developers.openai.com/api/docs/guides/voice-agents)는 단일 Realtime, 단계별 STT→텍스트 agent→TTS, 별도 backend를 가진 GPT-Live를 구분한다. 이것은 선택 가능한 구현 구조이며 친근함의 효과 보증은 아니다.

| 후보 | 이 제품의 장점 | 비용·검증할 문제 | 판단 |
| --- | --- | --- | --- |
| A. 현재 Realtime + 적용 경로 정합 + 간결한 캐릭터/교환 자료 | 현재 qualified-turn·RTC·중단 제어를 보존하며 원인을 좁힐 수 있음 | 발화 내용과 운율을 한 모델이 선택하므로 내용 제어가 제한적 | **첫 비교안** |
| B. 대화 내용을 텍스트로 작성한 뒤 streaming TTS | 말하기 전 내용·화자 근거·캐릭터 관점을 검사하고 같은 글로 음성만 비교 가능 | 단계별 지연, ASR 오류, 텍스트화하며 잃는 억양·감정, TTS의 낭독감 | A의 한계를 확인한 뒤 작은 별도 후보로 비교 |
| C. GPT-Live + 별도 backend | 연속 음성 상호작용과 backend 역할 분리 후보 | 기존 수동 commit/response 트리거·완료 event 가정과 호환되지 않음. 재생·중단·소음·상태 소유권 재설계 필요 | 현재 모델명만 바꾸는 교체안으로 채택하지 않음 |

B에서 현재 Realtime에 ‘이 글을 그대로 읽어라’고만 시키면 다시 지침 준수에 의존한다. 독립 Speech/TTS 단계로 내용과 표현을 나누는 시험이어야 한다. 병렬 생성·후보 재선택·재작성 검사를 매 턴 켜면 지연과 비용이 늘므로, 먼저 준비 시간 여유가 있는 시작 장면과 오프라인 비교에 한정한다. 낡은 통화 상태로 생성한 결과는 `contextGeneration`이 달라졌을 때 재생하지 않는다.

[GPT-Live migration 문서](https://developers.openai.com/api/docs/guides/live-migration)는 연속 음성 전송과 새 event lifecycle을 요구하며, backend 결과를 검사하는 것만으로 모든 음성을 멈출 수 없다고 설명한다. 현재의 cancel/clear ACK·실제 재생 이력·qualified 발화 보호를 검증 없이 제거하면 기존 소음 문제를 다시 만들 수 있다. hosted Realtime 음성 모델에 DPO·activation steering을 바로 적용할 수 있다고 가정하지 않는다. 그 접근은 지원되는 모델·경로와 실제 선호 데이터가 있을 때의 후속 연구다.

## 6. 음성의 자연스러움은 별도로 다룬다

텍스트의 과한 칭찬과, 듣고 있다는 짧은 소리는 같은 현상이 아니다. 응답 시작의 ‘알겠어요’ 반복, 사용자가 말하는 동안의 backchannel, 실제로 말할 차례를 가져오는 발화도 구분한다. [Live prompting 문서](https://developers.openai.com/api/docs/guides/live-prompting)는 backchannel과 interruption을 별도 항목으로 다루지만, 예시의 빈도나 문장 수를 이 제품의 의무 규칙으로 가져오지 않는다.

현재 `speed`는 재생 속도다. 속도 값을 바꿨다는 사실만으로 Mia·Alex·Juno의 운율·강조·웃음·응답 간격이 달라졌다고 볼 수 없다. 같은 내용·같은 voice에서 전달만 비교하고, 같은 voice·속도에서 내용만 비교한 뒤 최종 캐릭터/voice 조합을 듣는다.

소음 차단과 말할 차례 판단도 분리한다. 잡음·에코를 실제 사람 발화로 오인하는 문제와, 실제 ‘응/음’ 같은 청취 반응을 대화 중단 요청으로 취급하는 문제는 다르다. 현재 [수동 controller](../../web/qualified-turn-controls.js)는 provider의 speech-start와 최근 local 음성 증거가 함께 있으면 전사 내용 확인 전에 현재 응답을 취소한다. 전사는 나중에 비어 있지 않은지만 사용한다. 모든 짧은 맞장구가 실제로 이 조건을 통과한다는 뜻은 아니지만, 통과한 말소리를 대화 의도로 구분하는 단계는 없다. 운영 집계의 두 건은 provider VAD 경로이므로 이 수동 controller의 공백을 그 두 건이나 VOC의 원인으로 귀속하지 않는다.

음향 단계의 AEC/소음 억제·로컬/서버 발화 확인은 유지하고, 별도로 청취 반응/질문·정정/명시 중지/불확실을 현재 대화와 음성·전사로 구분하는 후보를 비교한다. ‘yeah’를 무시하는 단어 목록으로 만들지 않는다. AI 질문에 대한 답, 이야기 중 맞장구, ‘yeah, but…’는 역할이 다르다. 명시적 중지 버튼은 분류를 기다리지 않고 즉시 동작하게 두고, 분명한 음성 중지는 이용 가능한 증거에서 확인되는 즉시 처리한다. 부분 전사의 실제 제공 여부와 지연은 먼저 확인해야 한다.

의도 판정은 `input_item_id`, 당시 `playing_response_id`, `contextGeneration`에 묶어 늦은 결과가 새 응답을 취소하지 않게 한다. 맞장구 원문도 보존하되 새 AI 응답을 반드시 생성하는 발언권 요청과 구분한다. 불확실할 때 바로 취소하면 맞장구에 끊기고, 기다리면 진짜 끼어들기에 AI가 겹쳐 말할 수 있다. WebRTC 출력을 단순 mute/duck한다고 재생 위치가 정지하는 것은 아니다. 놓친 단어 없이 재개하려면 별도 출력 버퍼가 필요하므로 공짜인 해결책으로 제안하지 않는다.

소음 오검출, 맞장구에 의한 취소, 실제 끼어들기 누락, 명시 중지부터 실제 소리 정지까지 지연, 불필요한 재설명·놓친 음성을 나눠 측정한다. 긴 최소 발화 길이·큰 음량·고정 지연만 늘려 해결됐다고 판단하지 않는다.

## 7. 비교 실험과 도입 기준

### 지침 정합 뒤의 개발 비교

기존 soup/cafe/record-shop 사례는 개발용으로 고정한다. 새 holdout은 같은 6개 상황을 모든 캐릭터에 제공한다: 첫 접속·사용자 선행, 재접속의 열린 이야기, 결과 미상 계획과 정정, 서툰 일상 공유와 조언 거절, 서로 다른 취향, 표현 도움 뒤 원래 이야기 복귀.

제안 파일럿은 6상황×3캐릭터×2회=조건당 36에피소드다. 시작과 후속 2응답이면 조건당 최대 108응답이다. 기준안과 후보 하나부터 비교하고, 원인이 갈리지 않으면 여러 변경을 한꺼번에 늘리지 않는다. 이 규모는 실패 발견용 개발 예산이며 통계적 검정력 계산이 아니다. 모델 비교는 이력·voice·속도·입력·reasoning을 같게 하고 바꾸려는 변수만 바꾼다.

별도로 캐릭터별 3회 통화 사슬을 실행한다. 실제 첫 통화 저장으로 기억을 생성하고 다음 통화에 검색해 사용하며, 마지막에는 정정·제외를 넣는다. 작성된 handoff를 주입하는 시험과 구분한다. 텍스트/음성 입력 쌍, AI 선행/사용자 선행/동시 시작, 재생 중 짧은 청취 반응/실제 중지, 실제 휴대폰 내장 스피커/이어폰을 포함한다.

### 맹검 평가

조건명·모델명·버전을 숨기고 A/B 순서를 무작위화한다. 두 검토자가 독립 판정하고 동률·판단 불가·이견과 근거 구간도 남긴다. 한 대화의 여러 턴을 독립 표본으로 세지 않는다.

| 항목 | 판정할 행동 | 잘못된 대리 기준 |
| --- | --- | --- |
| 시작 | 이야기에 들어가기보다 기능·활동·주제 목록을 안내하는가 | 인사·이름·질문이 있으면 실패 |
| 반응 | 실제 디테일에 맞는 관찰·관점·궁금증이 있는가 | 원문 키워드를 반복하면 성공 |
| 과한 맞장구 | 근거 없이 칭찬·감정·성과를 덧붙이거나 관점을 사용자 쪽으로 바꾸는가 | ‘좋아요’나 축하 단어 금지 |
| 상호성·주도권 | 캐릭터가 참여하면서 사용자도 이야기 방향을 바꿀 수 있는가 | 매 턴 자기 의견·질문 의무 |
| 캐릭터 | 같은 조건에서 관점의 결이 일관되고 변화에 이유가 있는가 | 지정 소재를 자주 말하면 성공 |
| 연속성 | 필요한 과거 내용을 적절히 사용하고 현재 정정을 수용하는가 | 기억 언급 수·receipt가 많으면 성공 |
| 요청 대응 | 도움·거절·중지·짧게 요청을 실제 다음 행동에 반영하는가 | ‘알겠어요’라는 수락 문구 |
| 음성 | 억양·간격·중단과 재개가 편안하고 뜻을 해치지 않는가 | 빠르거나 짧으면 성공 |

좋은 소식의 축하, 사용자가 요청한 주제 선택지, 적절한 단순 맞장구는 정상 반례로 둔다. 평가가 캐릭터를 차갑거나 반대만 하는 방향으로 최적화하지 않게 한다.

주 결과는 쌍대 선호와 근거다. 요청하지 않은 수업 전환·거절 미반영·기억 오류 등은 별도 사건으로 기록한다. 의미가 같은 시작/마무리의 여러 통화 반복을 평가하고, 문장 길이·질문 수·통화 시간은 설명 변수로만 쓴다. 첫 소리까지 지연과 **첫 의미 있는 응답까지 지연**, 실제 재생·중단 정지 시간을 함께 본다. 시작을 채우는 상투어로 지연 지표만 좋게 만들지 않는다.

### 실제 사용자 확인과 도입

동의한 성인 6–8명의 반복 통화 형성평가부터 제안한다. 같은 캐릭터를 두 조건에서 두 번씩 경험하되 조건 순서를 교차 배정한다. 이 규모로 사용자 전체의 성공률이나 캐릭터 우열을 주장하지 않는다. 파일럿의 참가자 내 변동과 사전 정의한 실용적 차이로 후속 표본을 설계한다.

전달 계약→holdout 맹검→제한된 실제 통화 순으로 확대한다. 계정/캐릭터 혼합·잊은 정보 재등장·중지 제어의 재현 가능한 위반은 확대를 중단하고 수정한다. 품질은 시작·재접속·거절·도움 요청별 악화도 살펴 판단하며 임의의 ‘90%’ 하나로 합격시키지 않는다. 실사용 조건은 계정·캐릭터 단위로 고정해 재접속 때 서로 다른 캐릭터 상태가 섞이지 않게 한다. 문제가 생기면 이전 지침·자료 schema로 되돌리되 현재의 잊기·제외와 유효한 source revision을 다시 적용한다. 무효화된 기억은 rollback으로 되살리지 않으며 raw transcript·사용자 설정은 보존한다.

## 8. 최소 기록과 실제 수정 위치

평가용 기록은 `run/case/arc/call index`, 코드·모델·voice·입력 방식, 승인/관측 지침 revision과 일치 여부, 응답 상태·재생/중단 시점, 검토 조건·근거 구간이면 된다. 전체 지침·원문·오디오는 일반 진단 로그에 추가하지 않는다. 합성 또는 별도 동의 평가 저장소의 원문은 접근·보관 범위를 제한하고 삭제·제외를 전파한다. 실사용 집계는 개인 ID 없는 고정 enum별 개수부터 본다.

| 작업 묶음 | 수정 후보 | 범위 |
| --- | --- | --- |
| 적용 경로·지침 정합 | `web/app.js`, `web/realtime-requests.js`, `coach/index.ts`, 관련 diagnostics | 빌드/정책 협상, 승인 지침 보존, checkpoint ACK 상관, 전송 경로 평가 |
| 캐릭터 관점 | `coach/core.ts`와 별도 버전 profile | 작성된 관점·이유·조건을 사용자 정보와 분리 |
| 대화 교환 기억 | `conversation-memory.ts`, `temporal-context.ts`, `live-context.ts` 및 출처/재생 연결 schema | 실제 양쪽 발화·정정·제외·재생 상태. 기존 사용자 사실 검증 유지 |
| 자료 조립·예시 | `opening-policy.ts`, `coach/index.ts` | 현재 발화와 과거 교환 분리, 적절한 열린 이야기 선택, 상황별 예시 비교 |
| 품질 평가 | 기존 합성 생성기와 별도 holdout/rubric/음성 평가 | 지침 적용 증거, 실제 기억 경로, 맹검·청취·반복 통화 검증 |

구현은 첫 묶음부터 시작하고 한 후보씩 평가한다. 캐릭터 관점·공유 기억·음성 구조를 동시에 바꿔 무엇이 효과가 있었는지 알 수 없게 만들지 않는다.
